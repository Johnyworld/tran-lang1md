# 랑그릿사 (MD) 한글화 — 현황

## 대상 롬

```
Langrisser.md   524288 bytes (4Mbit)
SHA1  cc67c5a3b91e706b495eb561a95a038fff72b5da
MD5   4759f8db3ee29d85f7087886d813c04b
헤더  (C)T-25 1991.JAN / ラングリッサー / GM T-25103-00 / J
SRAM  있음 (0x01B0 "RA")
```

## 확정된 사실

- **평문 SJIS 텍스트 없음.** 롬 전체를 SJIS 2바이트 시퀀스로 스캔했으나 유효한 일본어 문장이
  헤더의 `ラングリッサー` 하나뿐. → 자체 코드 테이블 또는 압축.
- **폰트는 정적으로 못 찾음.** 두 가지 탐지를 돌렸고 둘 다 실패:
  - 1bpp 해석: 저엔트로피 후보 `0x2C000` 대역 → 글리프 아님(다른 테이블 데이터)
  - 4bpp 2색 해석: `0x5D800` / `0x5E800` / `0x61000` 이 니블 {0xD, 0xF}만 사용해 후보로
    잡혔으나 타일 렌더 결과 글리프 아님
- 16KB 블록 엔트로피가 전 구간 6.0~6.8로 균일 → **그래픽·텍스트 모두 압축 저장**으로 판단.

결론: 정적 분석으로는 진행 불가. 런타임 VRAM 덤프로 폰트 실물을 확보한 뒤,
그 비트패턴을 키로 롬 내 압축 스트림과 압축 해제 루틴을 역추적한다.

## VRAM 해석 결과 (해결됨)

덤프: `work/Mega Drive/Langrisser-vdp-vram-*.bin` (64KB, 프롤로그 화면, 4장 모두 동일)

ares Export 가 무반응이던 원인은 `Paths → Debugging` 미설정. 설정 후 정상 동작.

### 폰트 두 종류

**8x8 ASCII** — 타일 `0..95`, `타일 = 문자코드 - 0x20` (0x20..0x7F).
`PLAYER` / `ENEMY` / 숫자용.

**8x16 가나** — 세로로 붙은 두 타일이 한 글자.

| | |
|---|---|
| 아래 타일 (가나 본체) | 카타카나 `타일 = JIS X 0201 - 0x20` → `0xA1..0xDF` = `129..191` |
| | 히라가나 `타일 = JIS X 0201 + 0x20` → `0xA1..0xDF` = `193..255` |
| 위 타일 (탁점) | `101` = 공백, `106` = ゛, `107` = ゜ |

즉 `げ` = 아래 `け`(217) + 위 `゛`(106). 탁점을 별도 타일로 얹는 구조라
가나 본체는 71자만 있으면 된다.

### 화면 구조

본문 영역   3..34 칸 (32칸), 행 5·7·9·11·13
행 피치     타일 2행 = 16px

```

스크린샷과 한 글자도 틀리지 않음.

### 한글화 관점에서의 함의

- **세로는 공짜.** 게임이 이미 16px 행 피치에 타일 2행을 쓰므로 한글 16x16 이 그대로 맞는다.
  위 타일이 지금은 탁점 전용이지만 한글에선 글리프 상반부로 쓰면 된다.
- **가로가 문제.** 한글 1음절 = 가로 2칸 → 한 줄 32칸 = **한글 16자**.
  원문은 한 줄 32가나이므로 정보량이 거의 반으로 준다. 줄 수를 늘리거나
  본문 영역을 넓히는 조정이 필요할 수 있다.
- 한글 1음절 = 2x2 타일 4개. 위/아래 타일 행에 모두 써야 하므로
  현재 "위 행은 탁점만" 가정으로 짜인 렌더러 수정이 필요하다.

### 롬 내 폰트 위치 (해결됨)

VRAM 폰트 타일을 1bpp(잉크 = 색상 15)로 변환해 롬에서 검색 → **`0x3B09A`~`0x3B970` 확정**.
압축이 아니라 **1bpp 저장**이었다. 초기 4bpp 2색 탐지기가 놓친 이유가 이것.

저장 형식은 단순 배열이 아니다. 대부분 글리프는 8바이트 stride 지만,
빈 행이 있는 글자(`a` `c` `e` `g` 등)는 **6바이트로 줄어 있다** — 빈 행을 잘라낸 가변 길이.
어느 행이 잘렸는지 알려주는 헤더는 글리프 옆에 없으므로 별도 테이블이 있을 것으로 추정.
오프셋이 8바이트 정렬도 아니다(예: `A` = `0x3B224`, mod 8 = 4).

폰트를 가리키는 32비트 절대 포인터는 롬에 없다.
`0x1C820` 이 후보로 잡혔으나 `move.w #$0003, $B09A.w` 의 피연산자가 우연히 이어진 오탐.
뱅크 오프셋 또는 테이블 경유 참조로 보인다.

### 텍스트 인코딩 (해결됨)

**텍스트는 압축이 아니라 평문이었다.** 초기 검색이 빗나간 이유는 두 가지 —
탁점이 별도 바이트로 뒤에 붙어 문자열이 끊겼고, 카타카나가 별도 모드였다.

```
0x0D        줄바꿈
0x20..0x7D  ASCII 그대로 (0x20 = 공백)
0x7E        카타카나 모드 토글 (고유명사를 감싼다)
0xA1..0xDD  JIS X 0201 가나 — 기본 히라가나, 토글 중이면 카타카나
0xDE        탁점  ゛ (직전 글자에 결합)
0xDF        반탁점 ゜ (직전 글자에 결합)
0xFF        메시지 종료 (뒤에 0x00 이 따라오는 경우가 많다)
```

히라가나 바이트가 JIS X 0201 카타카나 코드와 그대로 같다.
카타카나는 같은 바이트를 `0x7E` 모드 안에서 쓴다. 폰트 타일이
히라가나/카타카나 두 벌로 나뉘어 있던 것과 대응된다.

검증: 프롤로그 블록을 디코드해 스크린샷과 일치 확인.

### 대본 위치와 규모

대본 블록 탐지는 검증된 블록의 바이트 알파벳을 기준으로 슬라이딩 윈도우
(64바이트 중 92% 이상)로 수행. `work/script_blocks.txt` 에 88개 블록 기록.
주 대본은 `0x33000`~`0x39A00` 에 집중.

```

## 주소지정 방식 (해결됨)

### 포인터 테이블은 20스테이지 메타데이터 전용

| 테이블 | 엔트리 | 내용 |
|---|---|---|
| `0x38A38` | 20 | 스테이지 이름 |
| `0x38BF2` | 20 | 스테이지 프롤로그 |
| `0x3962E` | 20 | 승리/패배 조건 |
| `0x2087C` | 14 | (미분류) |
| `0x3A322` | 11 | (미분류) |

### 본편 대사에는 포인터 테이블이 없다

delta 수열 지문으로 (2/4바이트 값) × (stride 2/4/6/8) 조합을 전수 탐색 → **전부 0건**.
탐색 코드는 알려진 테이블 `0x38BF2` 를 정확히 찾아내므로 코드 결함이 아니다.

실제 방식은 **68000 코드 안의 즉치(immediate)** 였다.

```
21 FC 00 03 35 4A E8 32   =   move.l #$0003354A, $E82C.w
```

`tools/refs.py` → `work/refs.json`

```
대본을 가리키는 코드 즉치   212개
  move.l #imm,(d16).w      157   (목적지 대부분 $E82C = 메시지 포인터 RAM 변수)
  lea imm.l,a0/a1/a2        54
  move.l #imm,(xxx).l        1
서로 다른 타겟 주소         153개
메시지 시작에 정확히 일치    97개
```

메시지는 `0xFF` 구분자로 빽빽하게 붙어 있고 사이에 이벤트 명령 바이트가 없다
(간격이 거의 전부 정확히 1바이트). 즉치 153개 < 메시지 896개 이므로,
즉치는 **대화의 시작점**을 가리키고 이후 메시지는 순차로 진행된다.
대화가 어디서 끝나는지(`0xFF 0x00` 가설은 기각 — 앵커 앞이 대부분 `0xFF` 단독)는
아직 규명되지 않았으나, **아래 재삽입 전략에서는 알 필요가 없다.**

### 재삽입 전략

in-place 로 고치면 길이 변화가 뒤쪽 전부를 밀어내므로, 대신
**대본 전체를 확장 영역(512KB → 1MB)으로 이설하고 즉치 212개를 재계산**한다.
메시지 순서와 구분자만 보존하면 순차 진행 동작이 그대로 유지되므로
대화 종료 조건을 몰라도 안전하다. 길이 제약도 사라진다.

## 렌더러 (해결됨)

### 메시지 인터프리터 `0x1536E`

`$E82C`(기준 포인터) → `$E818`(작업 포인터). 16비트 워드를 읽어 명령을 분기하고
`0xFF30DA` / `0xFF517C` 테이블을 인덱싱한다. 최상위 비트가 선 워드는 종료.

`0x15470` 에 **순차 진행이 코드로 확증**되어 있다 — 메시지를 건너뛸 때
포인터 산술이 아니라 `0xFF` 를 찾아 바이트를 하나씩 훑는다.

```
015470  move.b  (a1)+, d5
015472  cmpi.b  #$FF, d5
015476  bne     $15470
015478  move.b  (a1)+, d5        ; 한 번 더
01547A  cmpi.b  #$FF, d5
01547E  bne     $15478
```

따라서 대본을 이설하고 앵커만 재계산하면 순서·구분자 보존만으로 동작이 유지된다.

### 글리프 렌더러 `0x15576`

상태 변수:

| 주소 | 내용 |
|---|---|
| `$E818` | 작업 포인터 |
| `$E81C` | X (칼럼) |
| `$E81E` | Y (행) |
| `$E820` | 히라가나 모드 플래그 |

동작:

```
01557E  move.b  (a1)+, d6            텍스트 바이트
015580  cmpi.b  #$FF   -> 종료
015588  cmpi.b  #$0D   -> 줄바꿈
015594  eori.w  #$1, $E820           0x7E = 모드 플래그 토글
                                     (코덱의 히라가나 토글과 일치)
줄바꿈:
0155AC  move.w  $AEAA.w, $E81C       X 를 행 시작값으로
0155B4  addi.w  #$A, $E81C           + 10  (좌측 여백)
0155BC  addq.w  #$1, $E81E           Y += 1

글자 출력:
0155C4  move.w  $E81C, d1            d1 = X
0155CA  move.w  $E81E, d2            d2 = Y
0155D0  addq.w  #$1, $E81C           X += 1     <<< 칼럼 전진
0155D6  move.w  #$C000, d3           네임테이블 베이스
0155DA  move.w  #$8000, d4           타일 속성
0155EC  addi.w  #$40, d4             히라가나면 +0x40  <<< 타일 오프셋
0155F4  jsr     $5F2E                타일 1개 출력

탁점:
0155FC  cmpi.b  #$DF  (반탁점)
015602  cmpi.b  #$DE  (탁점)
015608  subq.w  #$1, d2              Y -= 1   <<< 윗줄에 찍는다
01560A  jsr     $5F2E
```

히라가나 `+0x40` 은 앞서 VRAM 에서 관측한 카타카나(129..191) / 히라가나(193..255)
타일 차이 64 와 정확히 일치한다. 탁점의 `Y-1` 도 "위 타일에 얹힌다" 는 관측과 일치.

### 바이트 → 타일 변환 테이블 `$62BC`

`$5EFE` 가 실제 타일을 찍는다. 핵심은 **256바이트 룩업 테이블**이다.

```
005F0C  lea.l   $62BC.l, a2
005F12  move.b  (a2, d6.w), d2      텍스트 바이트 -> 타일 번호
005F1C  or.w    d5, d2
005F1E  or.w    d4, d2              속성 결합 (히라가나면 0x40 이 여기 실림)
005F20  move.w  d1, (a1)+           VDP 주소
005F22  move.w  d2, (a1)+           타일 워드
```

앞서 "타일 = 바이트 + 0x20" 이라고 적은 것은 산술이 아니라 **이 테이블 내용을
관측한 결과**였다. 매핑은 테이블만 고쳐 자유롭게 재정의할 수 있다.

단 엔트리가 `move.b` 라 **타일 번호가 0..255 로 제한된다.** 현재 테이블은
서로 다른 타일 160종을 쓰고 최대값이 189, 미사용 타일 번호가 96개다.

### 타일 예산

```
프롤로그 번역문 고유 음절     53자
필요 타일 (음절당 2x2 = 4)   212개
테이블 미사용 타일            96개   -> 부족
가나 타일(129..189) 회수      61개
안 쓰는 ASCII 타일 회수       ~90개  -> 합계 약 247개, 212 들어감
```

가나 폰트를 덮어쓰므로 **다른 화면의 일본어는 깨진다.** 파이프라인 테스트에는
무해하며, 오히려 전체 게임에 동적 글리프 로딩이 필요한 이유를 실증한다.

MD VRAM 은 2048타일이고 이 화면이 이미 ~600타일을 쓴다. 대사 폰트 경로가
0..255 만 주소지정하므로, 전체 게임 한글화는 **메시지마다 필요한 글리프만
VRAM 에 실시간 업로드**하는 구조가 반드시 필요하다.

### 폰트 저장 형식 (정정)

앞서 "빈 행을 잘라낸 가변 길이" 라고 적었으나 오독이었다. 확정된 글리프 150개의
연속 간격 분포는 **8 이 129곳**, 14 가 8곳, 나머지는 산발적 대형 간격이다.
즉 stride 8 배열이 여러 구간으로 쪼개져 있고 구간 사이에 2바이트가 끼는 구조다.
간격 14 는 중간 글리프를 검색으로 찾지 못한 자리다(빈 글리프이거나
색상 15 기준 1bpp 변환이 일치하지 않은 경우).

이 형식은 더 파지 않는다. 기존 폰트를 고치는 대신 **자체 한글 타일 블록을
따로 업로드**하는 쪽이 형식 의존이 없고 동적 로딩에도 그대로 쓰인다.

### 그래픽 VRAM 업로드 루틴 `0x54AC`

```
0054B2  move.w  #$2700, sr           인터럽트 차단
0054CC  move.l  d0, $C00004.l        VDP 컨트롤 — d1 이 VRAM 주소
0054D4  lea.l   $C00000.l, a6        VDP 데이터 포트
0054E0  tst.b   (a0)+                최상위 비트로 압축/비압축 분기
0054E4  bsr.w   $55B2
0054F4  move.b  (a0)+, d5 / lsl #8 / move.b (a0)+, d5
0054FA  lea.l   (a0, d5.w), a1       16비트 오프셋으로 두 번째 스트림 진입
```

비트플레인 기반 자체 압축 코덱이다. 인자는 `d1` = VRAM 주소, `a1` = 소스.
그래픽이 압축이라던 초기 판단은 이 루틴 기준으로 맞았다(폰트만 1bpp 비압축).

한글 타일은 이 코덱을 역설계하는 대신 **비압축 업로드 루틴을 새로 짜서**
올린다. 형식을 우리가 정하는 쪽이 싸다.

## 부팅 체크섬 검사 (실측 확인)

`0x4630` 에 검사 루틴이 있고 **실제로 작동한다.** 체크섬을 고치지 않은 롬은
빨간 화면으로 죽는다(실측).

```
004630  lea.l   $200.w, a0
004634  sub.l   a0, d0          합산 길이 = 롬끝 - 0x200
004636  asr.l   #$1, d0         워드 개수
004640  add.w   (a0)+, d1       합산 루프
004642  dbra    d2, $4640
004646  dbra    d0, $4640
00464A  tst.w   $18e.w          <<< 헤더 체크섬이 0 이면 비교를 건너뛴다
00464E  beq.b   $465a
004650  lea.l   $18e.w, a0
004654  cmp.w   (a0), d1
004656  bne.w   $4840           불일치 -> 에러 화면
```

`0x18E` 에 `0000` 을 써두면 검사를 아예 건너뛴다(개발용 경로).
**작업 중에는 이 우회를 쓰고 최종 배포 패치에서만 정상 체크섬을 넣는다.**
매 빌드 재계산을 한 번 빠뜨리면 원인 불명의 빨간 화면을 보게 된다.

## 텍스트 파이프라인 실측 검증 (통과)

`tools/build.py` 로 프롤로그 자리에 27바이트 테스트 문자열을 넣고 ares 로 확인.
가정 7개가 모두 화면으로 검증됐다.

| 가정 | 결과 |
|---|---|
| 부팅 시 체크섬 검사 | 있음 — 미수정 롬은 빨간 화면 |
| 메시지 주소 `0x38C42` | 그 화면 맞음 |
| ASCII 경로 `0x20..0x7D` | `KOROM TEST` 정상 |
| 기본 모드 = 카타카나 | `テスト` 정상 |
| `0x7E` = 히라가나 토글 | `てすと` 정상 — 극성 정정이 옳았음 |
| `0xDE` = 앞 글자에 탁점 결합 | `デ` 로 합쳐짐 |
| `0x0D 0x0D` = 한 줄 | 줄 간격 원본과 동일 |

`0x0D` 하나는 `Y += 1`(타일 1행)이고 8x16 글리프는 2행을 쓰므로 한 줄에 두 개가
필요하다. 번역문 삽입 시에도 줄바꿈은 `0x0D 0x0D` 로 넣는다.

메시지를 27바이트로 잘라도 다음 프롤로그(별도 포인터 참조)는 정상 출력됐다.
종료자 뒤 잔여 바이트는 도달 불가임이 확인됐다.

### 한글화 수정 지점

1. **`0x1555D0` `addq.w #$1, $E81C` → `addq.w #$2`**
   한글 1음절 = 가로 2칸. 이 한 명령이 핵심.
2. **`$5F2E`(단일 타일 출력)** — 글리프 집합이 크게 늘어나므로 타일 인덱스
   계산 확장 필요. `d4` 속성 워드에 인덱스가 실린다.
3. **`0x1555B4` `addi.w #$A`** — 줄바꿈 시 좌측 여백. 본문 폭 조정 시 건드린다.
4. **탁점 경로(`0x1555FA`~`0x155616`)를 재활용한다.**
   `Y-1` 위치에 두 번째 타일을 찍는 메커니즘이 이미 있으므로,
   한글 글리프의 상반부를 여기에 그대로 얹으면 된다.
   렌더러를 새로 짜지 않아도 된다는 뜻이다.

4번이 이 프로젝트에서 가장 운이 좋은 부분이다. 게임이 이미
"현재 칸 위에 타일 하나 더 찍기" 경로를 갖고 있다.

**알려진 결함**: 앵커 없는 블록은 블록 시작 직전 `0xFF` 뒤에서 스캔하므로
정렬이 보장되지 않는다. 앵커 검증된 메시지는 `anchor: true` 로 표시된다
(1026개 중 165개). 미해석 제어 바이트 `0x00`(413) `0xFD`(164) `0x08`(67)
`0x0F`(19) 는 아직 규명되지 않았다.

## 출전 준비 화면 — 코드가 없어서 표를 갈아 끼웠다

용병 목록이 이렇게 나왔다.

```
표 원문           우리 번역          화면
65 ソルジャー      솔저    (2음절)    라이       (2칸)
66 ホースマン      호스맨   (3음절)    라이트      (3칸)
67 ライトエルフ    라이트엘프 (5음절)   라이트엘프    (5칸)
```

길이가 정확히 일치한다 — 클래스명이 **위치 코드**(타일 198..205)라서 세 줄이 같은
타일을 나눠 쓰고, 마지막에 그린 `라이트엘프` 가 앞 두 줄까지 덮었다. 이름판과 같은
사고이고, `클래스명은 그리기 11곳에 루프가 없으니 한 번에 하나만 보인다` 는 추론이
또 틀렸다. **코드에 루프가 없다는 것은 동시 노출을 부정하지 못한다.**

### 가나 코드를 훔치려다 측정으로 막혔다

공유 어휘로 바꾸려면 코드가 20개 넘게 필요한데 저바이트 코드 23개는 다 찼다.
남은 후보는 가나 코드(`0xA1..0xDF`)뿐이라 "이름표 78개가 안 쓰는 19개" 를 세어
쓰려 했다. **대사를 빼고 센 수였다.**

```
이름·클래스표 기준        안 쓰는 가나 코드 19개
대사 1026개까지 넣으면    1개 (0xA9)
```

`。` `「` `」` 가 그 안에 있었다. 전역 재매핑은 남은 일본어 전체를 깨뜨린다.

### 대체 코드 페이지 — 훅이 돌려주는 a2 가 곧 표다

우리 업로더가 `0x5FD4` 의 `lea $62BC.l, a2` 를 대신하므로, **돌려주는 a2 가 그
문자열의 코드->타일 표**다. 문자열마다 다른 표를 줄 수 있다는 뜻이다.

```
글리프 기록   [플래그][타일][N][ID x N]      플래그 bit0 = 대체 페이지로 그려라
대체 페이지   원본 256B 복사 + 본문 코드만 타일 212.. 로 (0x8A000)
```

그래서 용병 클래스 13개만 어휘 24자를 공유하는 기록 하나를 쓰고, 그 문자열들만
대체 페이지로 그려진다. 남은 일본어는 원본 표를 그대로 쓰므로 무사하다.

```
클래스  1 파이터      타일 198..205  원본 페이지 (위치 코드, 한 번에 하나)
클래스 65 솔저        타일 212..235  대체 페이지 (공유 어휘)
클래스 67 라이트엘프   타일 212..235  대체 페이지
가나 코드 D9/DA/DD -> 185/186/189   두 표에서 동일 = 지휘관 이름판 무사
```

타일 212..235 는 팝업 칸 꼬리(206..220)와 히라가나 폰트 영역(221..)에 걸친다. 이
화면에는 팝업도 히라가나도 없어서 안전하고, 겹치더라도 다시 그릴 때 각자 자기
글리프를 올리므로 낫는다.

**이 장치가 앞으로의 코드 부족을 푼다.** 동시에 보이는 것이 40칸을 넘지 않는 한,
코드 페이지를 하나 더 만들어 붙이면 된다.

## UI·시스템 마무리 — 남은 일본어를 기계로 셌다

`tools/uiscan.py`. UI 텍스트의 그리기 경로가 셋(낱개 `lea` / 창 레코드 종류 4 /
16B 고정 표)뿐임이 규명됐으므로, **`lea imm.l` 즉치를 전수로 훑어** 그 자리가
일본어 문자열인지 판정하면 목록이 나온다. 감으로 훑지 않기 위한 도구다.

### 레벨업·전직 팝업 3개 — 빈칸은 이름 자리였다

`'        は\n\nつぎのクラスになれます'` 의 공백 8개가 무엇인지가 관건이었다.
런타임이 문장에 이름을 써넣는 것이라면(롬이라 불가능하지만) 손댈 수 없다.
창 레코드의 `$aeb8` 콜백을 읽어 갈렸다 — **콜백이 이름과 클래스명을 (2,2) 부터
따로 그린다.** 공백은 그 자리를 비워 두는 여백일 뿐이다.

```
0x151AC  이름 -> 전직 후보 2개    창 0x32A8E  "클래스 체인지 가능!"
0x15218  이름 -> 새 클래스명 1개  창 0x32ABE  "           로 전직!"
0x1527A  이름                    창 0x32AF4  "레벨이 올랐다!"
```

한국어는 조사가 이름 끝소리에 따라 갈리므로(`레딘은` / `볼코프는`) **조사를 붙이지
않았다.** 이름 한 줄, 문장 한 줄로 끊으면 자연스럽고 정적 데이터로 가능하다.

### 후보 클래스 2개가 동시에 — 코드 페이지를 여러 장으로

`0x151F8` 의 `dbra d6` 가 2회(d6=1)다. 즉 전직 후보 **2개를 동시에** 그린다.
클래스명은 위치 코드라 뒤 후보가 앞 후보를 덮는다(용병 목록과 같은 사고).

클래스표 **사본**(`0x8B000`)을 만들어 후보 39개가 어휘 39자를 공유하게 하고, 후보를
그리는 `lea` 즉치 한 곳(`0x151FE`)만 사본으로 돌렸다. 상태창·전직 완료 팝업은
한 번에 하나만 보이므로 원래 표(위치 코드)를 그대로 쓴다.

그래서 코드 페이지를 **여러 장** 지원하도록 일반화했다.

```
기록 첫 바이트 = 페이지 번호   0 = 원본 $62BC / n = ALTTBL + (n-1)*256
페이지 1  용병 클래스 어휘 24자   타일 212..235
페이지 2  전직 후보 어휘 39자     타일 214..252
```

전직 팝업은 문장(팝업 칸 206..)과 후보(214..)가 한 화면이라, 문장이 214 를 넘어
먹으면 빌드가 죽는다. 같은 화면에 있는 것끼리의 겹침은 기계가 잡는다.

### 선택 창 제목 4개 — 압축 풀은 풀지 않는다

`アイテム選択` `兵士選択` `指揮官選択` `プロローグ` 는 두 번째 풀(리소스 `0x81`
-> VRAM `0x3800`, 타일 448)의 그래픽이고 **압축**이다.

압축 코덱을 역설계하지 않았다. 게임이 VRAM 에 올린 **직후 덮어쓴다** — 리소스를
올리는 `jsr $53B4` 세 곳(`0x1181C` `0x18C9C` `0x19038`)에 훅을 걸고 우리 비압축
타일 57개를 같은 자리에 쓴다. 승리/패배 라벨에서 통한 방법 그대로다.

```
음절 14개 (아이템선택·병사선택·지휘관선택·프롤로그) -> 타일 57개
풀 오프셋 98..154 — 원본 제목이 쓰던 98..159 안에서만 쓴다
서술자 4개는 원본 길이 안에서 in-place (27/28, 23/24, 27/28, 26/28)
```

같은 풀의 승리/패배 라벨(오프셋 74..93)과 겹치지 않는다.

### 팝업 두 갈래는 조건이 아니라 후보 수다

`0x14E32` 의 `bne` 를 조건 검사로 봤는데 아니었다. `$B8B6` 는 **후보 얼굴 그래픽을
VRAM 에 올리고 두 번째 후보가 있는지**를 돌려준다(`d7 < 0` 이면 1).

```
후보 2개 -> 창 0x32A8E  "클래스 체인지 가능!" + 후보 2개를 고르는 화면
후보 1개 -> 창 0x32ABE  "           로 전직!"  (바로 전직)
```

즉 전직 팝업 둘은 같은 흐름의 두 갈래다. 텍스트 배정은 그대로 맞다.

덤으로 알게 된 것: `$B8B6` 가 얼굴을 **VRAM 0xA000** 에 올린다 — 전투 메뉴 풀과 같은
자리다. 그 화면에서 메뉴 풀은 덮이고, 메뉴를 다시 쓸 때 게임이 리소스 0x7D 를 다시
올린다. `0xA000` 은 화면마다 용도가 바뀌는 스크래치 영역이다.

### 남은 것 — 이름을 여러 개 동시에 그리는 자리 (대사 뒤로 미룸)

`uiscan.py` 기준으로 창 레코드와 낱개 문자열은 **0개** 남았다. 표도 클래스·마법
·아이템은 전부 우리 것이다. 남은 것은 **이름표를 읽는 `lea` 18곳 중 10곳**이고,
그중 하나가 출전 준비 화면 위쪽의 **지휘관 이름판**이다.

실기에서 **아래 상태바**(`0x00C486`)가 이름만 가타카나로 남아 잡혔다 — `0xC438` 이
클래스명(`$E2F8`)을 그린 뒤 같은 줄에 이름(`$E2FA`)을 그리는 자리다. 한 번에 한 유닛만
보이므로 상태바 표(마커 `0x02`, 타일 124..127)로 돌렸다. 미전환은 **7곳**이다.

```
01083A 0114DE 012B18 013590 0140DC 0158DA 020BB2
```

그 7곳 중 둘은 **루프**다. 앞서 "이름 그리기 18곳에 루프가 없다" 고 적었는데
틀렸다 — 탐색 창이 좁아서 놓쳤다.

```
0x10828  지휘관 이름판 루프   a2 = $E698(유닛 포인터 배열), 이름 = 1(a3), d3 = 순번
0x114CA  지휘관 목록 창 루프   같은 모양. y = $E692 가 줄마다 +2
```

우리 이름 배정은 타일 192..197 여섯 칸을 돌려쓰므로 이 루프에서는 모든 줄이 마지막
이름으로 변한다. **코드 페이지만으로는 안 풀린다** — 페이지는 문자열(표 엔트리)이
고르는 것이고, 어느 슬롯에 누가 뜨는지는 런타임 값이다.

설계는 나왔다. 슬롯마다 배정을 따로 주면 된다.

```
페이지 p    코드 0x0E..0x13 -> 타일 (BASE + 6p)     슬롯 수만큼 페이지를 만든다
이름표 사본 슬롯마다 한 벌 (엔트리는 [0x01][페이지 기록] + 위치 코드, 1248B x 슬롯)
훅        그리기 호출에 걸어 a1 += 슬롯 x 표크기, 글리프는 훅이 NAMEIDS 로 직접 올린다
슬롯 번호  draw 시점에 d3 은 0xD000/0xC000 으로 덮여 있다. y($E692)가 줄마다 +2 이므로
          (E692 - 초기값)/2 로 복원한다 (초기값 = 4 + $E6F6, 0x114AA 에서 확정)
```

**막는 것은 타일 예산이다.** 목록 창은 최대 10줄이라 6칸 x 10 = 60칸이 필요하고,
그만큼 연속으로 비어 있는 자리는 **가나 폰트 타일 129..191(63칸)** 뿐이다. 그건
남은 일본어 대사를 다 옮긴 뒤에야 놀게 된다.

그래서 이 항목은 **대사 뒤로 미룬다.** 순서가 뒤집힌 것이 아니라, 예산이 대사
진행에 묶여 있다는 것이 이번에 드러났다. 지금 원문으로 두는 것이 안전한 상태다 —
우리 글리프가 그 타일을 건드리지 않으므로 온전한 일본어로 나온다(실측 확인).

## 테스트용 디버그 롬

레벨업·전직처럼 진도를 내야 보이는 화면을 확인하려고 만들었다.
`tools/debug_rom.py` → `work/korom_debug.md` (배포판과 파일을 분리한다).

### 클래스 스탯 표 `0x2C06C` (규명)

```
$B5A0  lea $2C06C, a0 / a0 += 클래스 x 128
```

클래스 번호는 이름표(`0x2B334`)와 같은 색인이다. 레코드 1 이 파이터고 값이 레딘의
L1 실측값과 정확히 맞아(HP10 AT23 DF21 MV6, 지휘범위 3) 확정했다. 상태창이 그리는
자리(`0x12770` 의 `$6(a2)` `$8(a2)` `$4(a2)` `$A(a2)`)에서 필드를 역추적했다.

| 오프셋 | 내용 |
|---|---|
| `+02` | HP — 전투 병력 수. 10 이 최대로 보이므로 건드리지 않는다 |
| `+04` | MP |
| `+06` | AT |
| `+08` | DF |
| `+0A` | MV |
| `+70` | 지휘범위 |
| `+78` `+7A` | 수정 A+ / D+ |
| `+66` | 이 클래스를 격파했을 때 주는 경험치 |
| `+7C` | 레벨업 경험치 문턱 / 8 |

같은 이름이 세 벌씩 있는 구조(1,2,3 파이터 / 4,5,6 로드 / 10,11,12 나이트)와
34..62 의 되풀이가 **광 진영 1..33 / 암 진영 34..62** 구획의 근거다.

처음에 `+7A/+7C` 를 수정 A+/D+ 로 적었는데 **틀렸다.** 볼코프(소드마스터 = 레코드 7)
의 실측값 `A+0 D+9` 와 맞춰 보니 그 레코드의 `+7A/+7C` 는 `9, 3` 이었다. `+78/+7A`
가 A+/D+ 이고 `+7C` 는 레벨업 문턱이다. 화면 실측값 하나가 라벨 셋을 갈랐다.

### 레벨·전직 규칙 (실측)

```
0x0D3B0  7(a1) += 획득 EXP        유닛 +07 = 누적 EXP, +08 = 레벨
0x0D3C0  문턱 = 클래스 +7C x 8    파이터 16 / 로드 32 / 소드마스터·나이트 24
0x0D3D2  레벨 9 이상 + 전직 후보 없음($FFE252 == -1) -> 레벨 정지
0x0D4D2  cmpi.b #$A, $8(a1)       **전직은 레벨 10 부터**
```

### 팝업이 뜨는 시점 — 스테이지 클리어 후 정산이다

여기서 한 번 더 틀렸다. "적 하나 잡으면 레벨업 팝업이 뜬다" 고 했는데, **전투 중에는
창이 안 뜬다.** 레벨업·전직 창은 스테이지 정산 시퀀스에서 돈다.

```
0x1CC20  move.l #$D372, d0 / jsr $485E    스테이지 정산이 레벨업 시퀀스를 push
0x0D3FC  $FFE250 = 0x5A                   레벨업 후 90프레임(1.5초) 대기
0x0D45C  subq.w #1, $FFE250 / bpl         다 되면 상태를 0xD4C2 로
0x0D4D2  cmpi.b #$A, $8(a1)               전직 검사 -> 팝업
```

전투 중 레벨업은 별 경로(`0x0F092`)이고 창 대신 연출 오브젝트를 띄운다. 문턱은
같은 자리(`+7C x 8`)를 쓰므로 디버그 롬에서는 전투 중에도 한 마리에 한 레벨 오른다.

경험치는 격파한 쪽 클래스 레코드의 `+66` 에서 온다(`0x0F080`).

### 그런데 실측에서 또 갈렸다 — 팝업은 스테이지 종료로도 안 뜬다

디버그 롬으로 확인한 결과 **레벨은 오르는데(LV 1 -> 2) 팝업이 안 뜬다.** 즉 전투 중
경로(`0x0F092`)만 돌고 팝업이 있는 시퀀스(`0xD372`)는 그 흐름에 없다.

`0xD372` 를 push 하는 자리(`0x1CC20`)는 씬 디스패처(`$F07C` 로 분기하는 `0x1CAE2`
대역) 뒤에 있고, **그 디스패처의 진입을 정적으로 못 찾았다** — 32비트 즉치 참조가
하나도 없어 테이블 경유로 보인다. 어느 화면인지는 미확정이다.

그래서 확인은 **강제 표시**로 돌렸다. `tools/debug_rom.py --force-popup=levelup|
classchange|promote` 가 **"마법을 못 씁니다"** 팝업의 레코드 즉치(`0x10528`)를 그 창으로
바꾼다. 트리거는 **마법이 없는 유닛으로 유닛 메뉴의 마법을 고르는 것**이고, 콜백
(`$aeb8`)은 그 자리에서 `clr` 되므로 **텍스트와 창 레이아웃만** 확인된다.

처음에 "아이템이 없습니다"(`0x11E8E`)를 트리거로 썼는데 **아이템이 없으면 커서가 그
항목에 아예 가지 않는다**(실측). 부를 수 없는 트리거는 쓸모가 없다 — 팝업을 고를 때
"그 조건에서 정말 커서가 가는가" 를 같이 봐야 한다.

교훈: "적 하나 잡으면 레벨업 팝업" -> "스테이지 끝나면" -> 둘 다 틀렸다. 코드로
확정한 것(문턱·전직 레벨 10·유닛 필드)과 **추측한 것(어느 화면에서 뜨는가)** 을
구분해서 적어야 한다.

### 디버그 롬이 바꾸는 것

기본값은 아군 계열(1..33) AT/DF 99, MP 99, MV 40, 지휘범위 8, **문턱 0**(한 마리
잡으면 레벨업), 그리고 **전직 레벨 조건 `0x0D4D5` 를 10 -> 1** 로 내린다. 즉 적
하나 잡으면 레벨업 → 곧바로 전직 팝업이 뜬다. `--weak-enemy` 는 암 진영 AT/DF 1.

**배포 빌드에는 들어가지 않는다.** 파일이 다르고(`work/korom_debug.md`), 헤더 노트
`0x1C8` 에 `DEBUG BUILD - NOT FOR RELEASE` 표식을 남기며, `tools/release_check.py`
가 스탯 표를 원본과 바이트 비교해 강화가 샜는지 본다. 걷어낼 것을 잊지 않으려고
사람 기억 대신 기계에 맡긴 것이다 — 자세한 목록은 [RELEASE.md](RELEASE.md).

덤으로 이 표는 **볼코프가 소드마스터**(레코드 7 = AT25 DF22)임을 확정해 줬다.
출전 준비 화면에서 그가 `라이트엘프` 로 보였던 것은 용병 목록과 타일이 겹친
버그였고, 그 판정이 스탯으로 교차 검증됐다.

## 프롤로그 화면 전문 — 문자열마다 코드 페이지

스테이지 2 화면에서 프롤로그가 한 줄만 나오고 패배 조건이 비어 보였다. **버그가
아니라 원고가 미완성**이었다 — `ko.tsv` 에 프롤로그 첫 줄과 승리 조건만 들어 있었고,
스테이지 1 만 전문이었다(141B vs 47B).

전문을 넣으려면 예산이 막혔다. 화면 세 문자열이 **합집합 하나**를 공유하는 구조라
스테이지 1 이 이미 64/64 였다. 그래서 코드 페이지를 문자열마다 하나씩 줬다.

```
프롤로그  페이지 0  타일 128..191  (64칸)   원본 가나 폰트 자리
승패조건  페이지 3  타일 192..231  (40칸)   원본 히라가나 폰트 자리
스테이지명 페이지 4  타일 232..255  (24칸)
```

타일 192..255 는 원본이 **히라가나 폰트**로 쓰던 자리다(원본 프롤로그 화면 VRAM
네임테이블에서 198..253 사용 확인). 우리 빌드의 그 화면에는 일본어가 하나도 없어
비어 있다 — 같은 화면에 남은 일본어가 없다는 것이 근거다.

같은 코드가 페이지마다 다른 타일을 가리키므로 **코드를 늘리지 않고** 예산이 셋으로
쪼개졌다. 전문을 넣은 뒤 최대치는 프롤로그 59/64(스테이지 7), 조건 17/40,
스테이지명 6/24 다.

20스테이지 전부 번역 완료. 줄 길이는 34칸 상한을 기계가 검사한다.

### 8x8 폰트의 한계 하나 — `ㅐ` / `ㅔ`

되읽기 검증에서 `빼앗긴` 이 `뻬앗긴` 으로 복원됐다. 데이터는 맞고, **Galmuri7 8x8
에서 `빼` 와 `뻬` 의 픽셀이 완전히 같다.** `배/베` `애/에` `래/레` 는 구분된다.
쌍자음 + `ㅐ/ㅔ` 조합만 겹치므로 그 조합을 피하면 되고, 지금 원고에는 `빼앗긴`
하나뿐이다(문맥상 오독 여지 없음).

## 실기에서 나온 남은 UI — 그래픽 라벨 6개 + 상태바 이름

`uiscan.py` 가 0개라고 한 뒤에도 화면에서 일본어가 나왔다. **문자열이 아니라 타일맵
라벨**이었고, 스캐너가 창 레코드만 훑고 있었기 때문이다. `tools/tilescan.py` 를 만들어
`$5CDC` 호출 61곳을 전수로 훑었다(호출 앞에서 `lea imm,a1` / `move.w #imm,d4` 를 찾는다.
오탐이 있으니 실측과 대조해야 한다).

### 전투씬 라벨 4개

```
0x0F8FE  d4 = 0x8588 + 라벨 x 30, 서술자 0xFB10 (10x3) 를 넷이 공유
         타일 1416/1446/1476/1506, 리소스 0x7E -> VRAM 0xB100
호출     0xF548 기본능력 / 0xF61C 레벨수정 / 0xF708 지휘수정 / 0xF7BA 지형효과
```

서술자를 공유하므로 **서술자는 손대지 않고 타일 픽셀만** 갈아 넣는다. 프레임까지
한 덩이(80x24px)라 원본 픽셀이 필요했다 — VRAM 덤프에서 떠서 판 내부(x4..75, y5..18)
만 판 색(2)으로 지우고 한글 4음절을 그렸다.

### 선택 창 제목 — 훅 자리가 틀렸다

로드 지점 세 곳(`move.w #$81,d1` 이 보이는 자리)에 훅을 걸었더니 출전 준비 화면에서
`지휘관선택` 이 원문으로 나왔다. **리소스 번호를 레지스터로 넘기는 자리**를 놓친 것이다.

```
0x53D2  movem.l (a7)+, d1-d2/a1 + rts  ->  jmp 우리 루틴
        그 movem 이 d1 을 진입 시 값(리소스 번호)으로 복원한다
        [리소스][VRAM][타일수][원본] 표(0x8F000)를 훑어 덮는다
```

로더 꼬리 한 곳이면 **어느 경로로 로드해도** 걸린다. 제목(0x81)과 전투씬 라벨(0x7E)이
이 표를 쓴다.

### 출전 준비 라벨 2개 — 소유 리소스를 몰라도 된다

`指揮官選択`(타일 256) / `位置選択`(타일 272). 타일 256..287 이 리소스 3 인지 0x82 인지
갈리지 않았다(둘 다 VRAM 0x2000 에 올라오고 둘 다 압축). 그래서 로드 시점이 아니라
**그리기 직전**(`jsr $5CDC` 두 자리)에 올린다 — 소유권을 몰라도 타이밍이 맞는다.

`指揮官選択` 은 원문이 5한자를 12px 로 눌러 넣은 것이라 16px 한글로는 4칸(64px)에
안 들어간다. `지휘관` 으로 줄였다(화면 문맥상 뜻이 살아 있다).

### 아래 상태바 이름 — 마커를 하나 더 뒀다

대사 중 상태바 이름이 `레딘ン` `호ル쟈에ク` 로 깨졌다. 이름표 미전환 자리
(`0x00F9BE` `0x00FA6C`, `$5F94` 로 그린다)가 원본 가나를 읽는데 우리 글리프가 그 타일을
덮은 것이다. `$5F60`/`$5F7A`/`$5F94` 가 모두 `0x5FAA` 로 합쳐지므로 우리 훅은 지난다.

대사 이름판(타일 192..197)과 한 화면이므로 타일을 따로 줘야 하는데, **기록 색인이
1바이트(최대 256개)**라 이름표 사본용 기록 78개를 더 만들 자리가 없었다. 그래서
마커를 하나 더 뒀다.

```
[0x01][k]  기록 k 그대로
[0x02][k]  기록 k 의 글리프를 쓰되 페이지·타일을 상태바용(페이지 6 / 타일 124)으로 덮는다
```

타일 124..127 은 덤프 11장 전부에서 비어 있고(창 테두리는 110..118), 이름은 최대
4음절이라 4칸으로 충분하다.

### 코드 페이지 현황

```
0 원본 $62BC          1 용병 클래스 221..244    2 전직 후보 214..252
3 승패조건 192..231    4 스테이지명 232..255     5 상태창 라벨 245..250
6 상태바 이름 124..127 (이름 코드 0x0E..0x11 재매핑)
```

```
폰트 타일 37개   안전한 타일 자리에 Galmuri7 8x8 1bpp 글리프 덮어쓰기
$62BC 37엔트리   한글 바이트 코드(0x7F..) -> 타일 번호
대사 79바이트    0x38C42 (원본 자리 186B)
+ 체크섬 우회    0x18E = 0000
```

실기 해상도에서 8x8 한글의 가독성은 확대 미리보기 인상보다 훨씬 낫다.
수직 위치도 줄 안에 자연스럽게 앉는다(렌더러가 가나 하단 타일 행에 찍지만
어색하지 않음).

### 실패에서 배운 것 — 단일 스냅샷으로 타일 사용 여부를 판정하면 안 된다

첫 빌드는 VRAM 스냅샷 한 장에서 "화면에 없는 타일 = 미사용" 으로 판정해
ASCII 타일 36개를 덮어썼다. 그중 타일 17(`1`)이 스테이지 번호에 쓰여
제목이 `고.おうじょう...` 로 깨졌다.

같은 화면이라도 게임은 시점마다 다른 것을 그린다. 스냅샷은 **그 순간** 쓰는
타일만 알려준다. 숫자·알파벳은 UI 전반에 등장하므로 ASCII 영역(0..95)은
통째로 제외하고 가나 영역만 쓴다.

### 테스트 롬의 제약 (최종본에는 해당 없음)

덮어쓸 수 있는 안전 타일이 40개뿐이라 번역문의 **고유 음절을 37자로** 맞췄다.
같은 글자를 여러 번 쓰는 것은 공짜이므로 제약은 글자 수가 아니라 음절 종류 수다.
8x8 은 한 줄 34칸에 34자가 들어가므로 칸은 넉넉하다(최대 21/34 사용).

이 제약은 "기존 폰트 타일을 훔쳐 쓴다" 는 임시 방편에서 나온 것이다.
최종본은 대본이 전부 한글이 되어 가나 타일 전체를 회수할 수 있고,
그때는 메시지별 동적 글리프 업로드로 간다.

## 16x16 시도 — 실패 (기록)

`tools/patch_hangul16.py`. ASM 없이 16x16 을 만들려는 요령이었다.

`0x0D` 은 `Y += 1`, 즉 타일 한 행만 내려간다(`$6604` 의 `lsl.w #$7, d2` = `Y * 0x80`,
행 피치 0x80 = 64엔트리 = 한 타일 행). 그래서 한 줄을 두 번 써서
`[상반부 타일들] 0x0D [하반부 타일들]` 로 깔면 세로로 붙은 16x16 이 될 것으로 봤다.

**결과: 하반부 한 줄만 화면에 나왔다.**

검증한 것 — 모두 정상이었다:
- 메시지 바이트: 상반부 32B + `0x0D` + 하반부 32B 로 정확히 기록됨
- `safe_tiles.json` 에 중복 롬 오프셋 없음 (타일 40개 / 오프셋 40개)
- Galmuri11 글리프는 상·하반부 각각 4~5행씩 잉크가 있음 (상반부가 비어서가 아님)
- `$6604` 주소 계산상 `0x0D` 하나 = 8px 가 맞음

남은 가설은 두 줄이 같은 행에 겹쳐 그려져 나중에 쓴 하반부가 상반부를 덮었다는
것이다. 확정하려면 이 롬으로 VRAM 을 떠서 네임테이블을 봐야 한다.

**더 파지 않기로 했다.** 16x16 을 제대로 하려면 글리프 상하반부를 한 번에 찍는
렌더러 코드를 새로 써야 하고, 이 요령은 그걸 피하려던 우회였다. 동적 글리프
업로드를 만들 때 68000 코드를 쓰게 되므로 렌더러도 그때 같이 손대는 것이 맞다.
지금 원인을 파는 것은 곧 버릴 코드를 디버깅하는 것이다.

### 결론

```
8x8   채택. 5줄 전체 정상, 실기 가독성 충분, ASM 불필요
16x16 보류. 렌더러 신규 작성이 전제 — 동적 업로드 작업 때 재검토
```

## 동적 글리프 업로드 — 3회 실패, 원인 규명

`tools/asm.py`(손 어셈블 68000 + capstone 왕복 검증), `tools/build_dynamic.py`.

### 검증된 성과 (한글 출력과 무관하게 유효)

- 롬 1MB 확장이 부팅에 문제없다
- 대본을 `0x90000` 으로 이설하고 포인터 테이블을 고쳐도 동작한다
- 손으로 어셈블한 68000 코드를 롬에 심어도 부팅이 깨지지 않는다
- 텍스트 코드를 `0x7F..0xA0` / `0xE0..0xFD` 로 제한하면 남은 일본어가 온전히
  보존된다. `$62BC` 를 항등 매핑하면 가나 바이트(0xA1..0xDF)를 덮어써
  제목·승패 조건문이 깨진다(실측 확인).
- 롬에 빈 공간이 0바이트다. 확장 없이는 코드를 넣을 자리가 없다.

### 실패 원인 세 가지 (순서대로 드러남)

1. **`0x1556C` 는 죽은 코드다.**
   ```
   015560  move.w #$2, d0
   015564  cmpi.w #$2, d0
   015568  beq.w  $15650    <- d0 은 항상 2 이므로 항상 분기
   01556C  ...              <- 도달하지 않는다
   ```
2. **`$E818 == $E82C` 로 메시지 시작을 판별할 수 없다.**
   인터프리터가 `0x1536E` 에서 두 값을 같게 만든 뒤 워드를 읽어가며 포인터를
   전진시켜 `$E818` 에 다시 쓴다. 텍스트 렌더 시점엔 이미 다르다.
   → 우리가 심은 마커 바이트(`0xFE`)로 판별하도록 바꿨다.
3. **프롤로그는 `$E818`/`$E82C` 경로를 쓰지 않는다.**
   프롤로그 화면의 CPU RAM 덤프에서 `$E818` `$E82C` `$E81C` `$E81E` `$E820` 이
   **전부 0** 이고, 프롤로그 텍스트 주소(`0x38C42`)가 워크 RAM 어디에도 없다.
   포인터 테이블에서 읽어 레지스터로만 쓰고 버린다는 뜻이다.
   `0x15576` 과 `0x15650` 은 전투 중 대사용 경로다.

### 다음 시도의 방향

메시지 렌더러마다 훅을 거는 방식은 텍스트 경로가 여러 개(프롤로그·전투 대사·
메뉴)라서 경로별로 다 찾아야 한다. 대신 **모든 텍스트 경로가 공유하는
타일 출력 루틴 `$5EFE` 에 훅을 거는 것**이 경로 독립적이다.

`$5EFE` 는 `$62BC` 를 참조해 타일 하나를 찍는 유일한 지점이므로, 여기서
"이 코드가 한글 범위면 글리프를 슬롯에 올리고 그 슬롯 번호로 찍는다" 를
구현하면 어느 경로든 동작한다. 렌더러가 타이프라이터식으로 글자를 하나씩
그리므로 글자당 타일 1개 업로드는 비용도 감당 가능하다.

슬롯 배정 전략이 남은 설계 문제다. 한 화면에 최대 170자가 뜨는데 슬롯은
94개(가나를 전부 회수하면 ~160개)라, 화면 단위 중복 제거나 라운드로빈 중
어느 쪽이 안전한지 따져야 한다.

## 동적 글리프 업로드 성공 (4번째 시도)

프롤로그 5줄이 완전판 56글리프로 출력된다. **음절 37자 제약이 사라졌다.**

### 통한 이유 — 순서를 바꿨다

1~3차는 코드를 읽어 훅 지점을 추론했고 모두 빗나갔다. 4차는 **포인터 테이블
`0x38BF2` 를 누가 읽는지 역추적**해 실제 호출 지점을 찾았다.

```
018CF4  move.w  $AE6C.w, d7        스테이지 번호
018CF8  lsl.w   #$2, d7
018D18  lea     $38BF2.l, a1       프롤로그 테이블
018D1E  movea.l (a1, d7.w), a1     a1 = 문자열 주소  <- 레지스터로 직접
018D2A  jsr     $5F60.l            <- 이 6바이트를 우리 루틴 호출로 교체
```

주소가 RAM 변수가 아니라 `a1` 에 실려 온다. `$E818` 을 볼 필요가 없고
이 자리는 프롤로그 화면마다 정확히 한 번 실행된다.

`tools/asm.py: build_uploader_a1()` — `d1..d5` 는 `$5F60` 의 인자라 `movem` 으로
전부 보존하고 `d0` 만 쓴다(`$5F60` 이 진입 후 스스로 채우는 것을 확인).
`movem` 마스크 규약은 게임 자체 코드(`0x54AC` 의 `48e7fffe`)와 대조해 검증했다.
끝에서 `jmp $5F60` 으로 꼬리호출해 원래 호출을 이어받는다.

배치: 업로더 `0x80000`, 글리프 테이블 `0x81000`, 이설 메시지 `0x90000`.

### 알려진 결함 — 승패 조건문이 깨진다

글리프 슬롯이 타일 128번부터인데, 같은 화면에 남은 **일본어 승패 조건문이 그
가나 타일을 쓴다.** 프롤로그 본문이 먼저 그려져(`0x18D2A`) 타일을 한글로 덮고,
그 다음 조건문이 그려지므로(`0x18D42`) 덮인 타일이 보인다.

최종본에서는 전부 한글이 되어 가나 타일이 놀기 때문에 문제가 되지 않는다.
지금은 한 화면에 두 언어가 섞여 생긴 충돌이다.

**화면 단위로 해결해야 한다.** 네임테이블은 타일 *번호* 만 들고 있으므로,
나중에 그 타일의 픽셀을 바꾸면 먼저 그려진 글자의 모양까지 바뀐다. 즉 한 화면에
동시에 보이는 모든 문자열은 **하나의 일관된 타일 배정을 공유**해야 한다.

다음 단계: 첫 draw(`0x18D12` 스테이지명)에 훅을 걸어 그 화면 세 문자열
(스테이지명·프롤로그·승패조건)의 글리프 합집합을 한 번에 올리고, 각 문자열이
공유 슬롯을 참조하게 한다. 그러면 충돌이 사라지고 화면이 전부 한글이 된다.

## 프롤로그 화면 전체 한글화 완료

`tools/build_screen.py` → `work/korom_screen.md`. 화면 확인 완료.
스테이지명·프롤로그 5줄·승패 조건문이 전부 한글로 정상 출력되고 위치도 맞다.

### 화면 단위 슬롯 공유

네임테이블은 타일 *번호* 만 들고 있다. 나중에 그 타일의 픽셀을 바꾸면 먼저
그려진 글자의 모양까지 바뀐다. 그래서 한 화면에 동시에 보이는 문자열들은
**하나의 일관된 타일 배정을 공유해야** 한다.

프롤로그 화면 렌더러 `0x18CE8` 이 세 문자열을 순서대로 그린다.

| 호출 | 테이블 | 위치 | 처리 |
|---|---|---|---|
| `0x18D12` | `$38A38` 스테이지명 | X=12 Y=3 | **훅** — 합집합 전체 업로드 |
| `0x18D2A` | `$38BF2` 프롤로그 | X=3 Y=5 | 원본 유지 |
| `0x18D42` | `$3962E` 승패조건 | X=9 Y=15 | 원본 유지 |

첫 draw 에만 훅을 걸고 세 문자열 글리프의 합집합(64개)을 한 번에 올린다.
헤더(마커+ID 목록)는 첫 문자열만 갖고 나머지 둘은 본문뿐이다.

글리프 합집합 64개 / 코드 64개 — 여유가 0 이다.

### 이 단계에서 겪은 실수

**줄바꿈을 이중 적용했다.** 게임은 시각적 한 줄에 `0x0D` 두 개가 필요하다.
`encode()` 가 `\n` 하나를 `0x0D` 두 개로 펼치는데 `ko.tsv` 에도 `\n\n` 을 적어
네 개가 되어 32px 내려갔다. → `ko.tsv` 는 시각적 줄 수만 적는다.

**한 번에 세 가지를 동시에 고쳐 원인을 못 갈랐다.** 프롤로그가 사라진 원인은
줄바꿈 하나였는데, 같은 빌드에서 저바이트 코드 제거와 글리프 감축까지 같이
했다. 다음부터 하나씩 바꾼다.

**`0x0E..0x1F` 코드는 아마 멀쩡하다.** 사라진 원인이 줄바꿈으로 확정됐으므로
예방적으로 뺀 저바이트 18개는 쓸 수 있을 가능성이 크다. 지금 코드 여유가 0 이라
나중에 필요해지면 이것부터 검증한다.

### 남은 일본어·영어

**`PLAYER` / `ENEMY` / `FRIENDLY` / `VS` — 번역하지 않는다 (결정됨).**
어려운 단어가 아니고 그대로 읽히므로 손대지 않는다. ASCII 폰트로
`0x386CA` 등에 있고 `jsr $5F7A` 로 그려진다(다른 루틴). 기술적으로는 가능하다 —
8x8 한글은 음절당 1칸이라 `플레이어`(4칸)가 `PLAYER`(6칸)보다 오히려 짧다.
하지만 가치가 낮고 화면 글리프 예산이 이미 64/64 이므로 하지 않는다.

**`勝利` / `敗北` — 교체 예정.**
폰트가 아니라 그래픽이다. VRAM 타일 `522..541` = 4칸 x 5행 = 32x40px 블록에
두 라벨이 세로로 담겨 있다. 색상 구성은 13(배경)/15/14(외곽선).

조사 결과:
- 4bpp 원형은 롬에 없다 → 그대로 저장된 것이 아니다
- **1bpp(잉크=15) 변환형은 롬 `0x060872`~`0x06090A` 에서 8개가 유일하게 특정된다**
  즉 압축 그래픽 코덱을 역설계할 필요가 없다
- 찾힌 8개는 블록의 1행·3행이고 스트라이드가 16이다. 사이에 끼인 8바이트가
  색상 14 플레인일 것으로 봤으나 **틀렸다**(0/8 불일치). 저장 순서나 인터리브
  방식이 다르다.

형식을 추측으로 맞추지 말고 **이 타일을 VRAM 에 올리는 코드를 찾아 읽는다**
(프롤로그에서 통한 역추적). 타일 522 의 VRAM 주소는 `522*32 = 0x4140` 이므로
그 주소를 만드는 코드를 찾는 것이 출발점이다.

**교체 완료.** `승리`/`패배` 를 16x16 한글로 렌더해 같은 VRAM 자리에 덮어쓴다.
`tools/build_screen.py: make_labels()`, 데이터는 `0x82000`, 업로더가 20타일을
VRAM `0x4140` 으로 올린다.

원본 형식(타일당 16B = 색상15 마스크 + 색상14+15 합집합)까지 알아냈으나
**필요 없었다.** 업로더가 임의 타일을 임의 VRAM 주소에 쓰므로 우리 비압축 4bpp
타일로 덮으면 끝이다. "원본을 해석해야 한다" 는 가정이 헛수고였다 —
덮어쓸 수 있으면 읽을 필요가 없다.

| Galmuri11 + 사방 외곽선 | 획이 깨져 보임 |
| Galmuri11 Bold + 사방 외곽선 | 뭉침 |
| Bold + 우하단 그림자 | 너무 굵음 |
| Galmuri11 + 그림자 | `ㅐ` 의 두 세로획 틈이 메워져 `배`가 `버`로 |
| Galmuri11 장식 없음 | 여전히 `패버` — **폰트 자체의 한계였다** |
| **둥근모꼴 장식 없음** | **채택** |

16x16 한글은 획 간격이 좁아 어떤 장식도 획을 붙인다. 장식은 넣지 않는다.

마지막 원인이 핵심이었다. Galmuri11 은 `ㅂ` 이 16px 중 2..7열을 써서 `ㅐ` 에
9..11열만 남고, 세로획 두 개가 못 들어가 한 획 + 돌기로 압축된다. `패`(ㅍ+ㅐ)는
`ㅍ` 이 한 열 좁아 멀쩡하다. 즉 폰트 차원의 구조적 한계이며 렌더링으로는 못 고친다.

그래서 **`배`/`버` 픽셀 차이를 재서 폰트를 골랐다.**

```
프리텐다드 Bold    69   잉크 100   너무 굵음
둥근모꼴           50   잉크 101   획 1px, 자모가 셀을 꽉 채움  <- 채택
프리텐다드 일반     38   잉크  51   가늘고 여백 많음
Galmuri11          9   잉크  37   구분 불가
```

픽셀 전용 폰트만 후보로 본 것이 좁은 판단이었다. 자모 간격이 넓으면 16px 에서
더 잘 읽힌다. 앞으로 폰트 선택은 판별 지표를 재서 한다.

세로 위치는 +4px 내렸다 — 글리프 잉크가 16px 셀의 y=3..12 에 몰려 있어
그대로 두면 조건문(화면 행 15·17)보다 위로 치우친다.

## 본편 대사 — 경로 규명 완료

`0x1533A` 를 읽어 대사 시스템 전체를 갈랐다. 프롤로그와 **같은 렌더러**를 쓴다는 것이
핵심이고, 덕분에 글리프·코드 배정을 그대로 재사용한다.

### 호출 경로

전투·이벤트 대사는 예외 없이 이 형태로 시작한다 (코드 즉치 145곳):

```
move.l  #메시지주소, $E82C.w
move.l  #$1533A, d0
jsr     $485E.l              <- 코루틴 push ($8010 = d0)
```

`$485E` 는 상태머신 서브루틴 push 이고 `0x1533A` 가 메시지 인터프리터다.

```
0x1533A  인터프리터 진입      clr.w $E824 / a1 = $E82C -> $E818
0x1537A  메시지 시작          워드 W 를 읽는다 (상위비트가 서면 체인 끝)
0x154FE  창 열기              $aeb8 = 0x1579A 를 걸고 $879C 호출
0x1579A  이름판 그리기        $E818 을 본문으로 전진시킨 뒤 이름 렌더
0x15650  본문 그리기          a1 = $E818 -> jsr $60BE
0x156CC  다음 메시지          정렬 후 워드 확인 -> 0x1537A 로
```

**`$60BE` 는 `$5F60` 에 카메라 오프셋만 더하는 껍데기다.** 즉 프롤로그와 본편 대사가
같은 문자열 렌더러를 쓴다. 코드->타일 표 `$62BC` 도, 8x8 글리프 슬롯도 그대로 통한다.
"대사는 다른 경로" 라는 이전 판단은 틀렸다 — 포인터가 오는 길만 다르다.

`0x15576` 의 한 글자씩 타이핑하는 경로는 **죽은 코드**다. `0x15560` 이 `d0` 에 2 를
넣고 바로 `cmpi.w #2` 로 비교해 분기가 항상 성립한다. `0x157F8` 의 두 번째 이름판
렌더러도 참조가 없다(절대·상대 전수 확인).

### 스트림 문법 (chain.py)

번역 단위는 문자열이 아니라 **체인**이다. 앵커 하나에 대화 한 덩이가 이어 붙어 있다.

```
message := W:word  str1 0xFF  str2 0xFF        (메시지 시작은 짝수 정렬)
chain   := message*                            (W 의 상위비트가 서면 종료)
```

`W` 는 화자·연출 코드. `0x1F4` = `$E83A` 참조, `0x50..0xA0` = `$E82A` 설정 후 창만 열기,
그 밖 = 유닛 표 참조(`0xA1` 이상은 유닛 목록 끝에서 역순).

**문자열 두 칸 중 하나만 본문이고 선택은 런타임 `$E824`** 다 (화자 표에서 온다).
`$E824 != 0` 이면 `0x157BA` 가 str1 을 건너뛰어 str2 가 본문이 된다. 실제 데이터는
쓰지 않는 칸을 비워 두거나(대부분) 같은 문장을 복사해 둔다(`W` 가 `0x50..0xA0` 인 경우).

여기서 한참 헤맸다. `str1` 이 본문이라고 단정하고 읽으니 스테이지 1 첫 대화가
"아무것도 그리지 않고 체인이 끝난다" 는 모순이 나왔다. 모순을 무시하지 않고 `$E818`
을 쓰는 코드를 전수 조사해(`ffffe818` 참조 16곳) `0x157AA` 의 이름판 렌더러가
`$E818` 을 전진시키는 것을 찾았다. **모순은 대개 놓친 코드가 있다는 신호다.**

빌드는 `$E824` 를 알 필요가 없다. **원본의 모양을 그대로 보존**하면 된다 — 비어 있던
칸은 비우고, 본문이던 칸에 번역을 넣는다. 판단이 데이터에 이미 들어 있다.

### 훅 하나로 충분하다 — `0x157C8`

`0x1579A` 안의 `move.l a1, $E818` (6바이트) 을 `jsr 업로더` 로 바꾼다.
`asm.build_uploader_msg`. 그 자리가 유일한 훅으로 충분한 이유:

- `a1` 이 이미 **본문 문자열**을 가리킨다. str1/str2 판단이 이미 끝난 자리다.
- 이름판(`0x157EC`)·본문(`0x15650`) 두 그리기보다 **먼저** 실행된다. 네임테이블은
  타일 번호만 들고 있으니 그리기 전에 픽셀을 올려야 한다.
- 메시지마다 창을 다시 열므로(`0x154FE`) 메시지마다 정확히 한 번 실행된다.

메시지마다 창을 다시 그린다는 것은 **대화 단위 합집합이 필요없다**는 뜻이다.
한 화면에 한 메시지만 보이므로 메시지 단위로 64슬롯을 다시 쓸 수 있다.
프롤로그에서 겪은 "화면 단위 공유" 문제가 여기서는 이름판만 걸린다.

### 이름판 — 원본 표를 건드리지 않는다

이름은 `0x2AE64` 의 16바이트 x 78 표에서 오고, 이름판은 6칸이다.
같은 표를 유닛 상태창 등 다른 UI 도 읽으므로 **원본 표는 그대로 두고**
이름판 렌더러가 보는 포인터 즉치(`0x157D8`)만 우리 표로 돌린다.

우리 표의 문자열은 **위치 코드**다 — k 번째 한글 칸은 항상 코드 `0x0E+k`.
업로더가 `$E82A`(이름 인덱스)로 글리프 ID 표를 찾아 타일 `192+k` 에 올린다.
그래서 표에는 자리만 적으면 되고, 아직 번역하지 않은 일본어 메시지도 이름판은
한글로 나온다(이름 글리프 업로드는 마커와 무관하게 항상 실행).

`0x0E..0x13` 은 STATUS 에서 미검증으로 남겨둔 저바이트 코드 구간이다. 이름 문자열은
`$5F60` 만 읽으므로(인터프리터는 `0xFF` 만 훑는다) 이 검증을 여기서 같이 한다.

## 대사 파이프라인 실측 확인 (통과)

스테이지 1 이벤트 1 (`0x333BA` → `0x0B0000`, 9메시지). 조건이 `0x3306A` = `$ae72 == 1`
이라 스테이지 1 시작 직후 재생된다 — 확인 비용이 가장 싼 자리라서 골랐다.

첫 메시지가 본문·이름판 모두 한글로 정상 출력. 세 가지가 한 번에 통과했다:

- **본문** — 훅 `0x157C8`, 슬롯 128..191, 줄바꿈 `0x0D` 두 개, 21칸 한 줄
- **이름판** — 위치 코드 + `$E82A` 로 찾는 글리프 ID 표 + 타일 192..197
- **저바이트 코드 `0x0E..0x13`** — 미검증으로 남겨뒀던 구간이 멀쩡함이 확인됐다.
  프롤로그가 사라진 원인은 줄바꿈이었지 저바이트 코드가 아니었다는 추론이 맞았다.

### 남은 확인 (플레이가 필요해 미룬 것)

- 9메시지 연속 재생에서 앞 메시지 글자가 뒤 메시지 글리프로 변형되지 않는가
  (메시지마다 창을 다시 그린다는 추론의 검증)
- 대사창 밖 일본어 UI 가 깨지는 범위 — 타일 128..197 을 덮으므로 화면에 가나가
  남아 있으면 같이 변한다

### 눈에 띈 것 — 낱말 사이가 넓어 보인다

공백은 한 칸(코드 `0x20`)이고 게임 ASCII 폰트의 공백·`!` 글리프가 8px 셀 안에서
가운데 정렬돼 있어 양옆 여백이 더해진 것이다. 원문 일본어도 같은 폰트를 쓰므로
원본과 같은 간격이며, 우리 쪽 버그가 아니다. 줄이려면 낱말 사이를 붙여 쓰면 된다.

## 번역 진행 도구

```
tools/events.py   스테이지 이벤트 표(0x32BB0) -> 스테이지·이벤트별 앵커
tools/sheet.py    translation/dialogue.tsv 를 이야기 순서로 재생성 (기존 번역 보존)
tools/chain.py    앵커 하나 -> 대화 한 덩이
```

`refs.json` 대신 **`21fc <즉치> e82c` 8바이트 패턴을 전수 스캔**해 앵커를 찾는다
(`events.e82c_sites`). refs.json 은 대본 주소 범위로 걸러낸 목록이라 이벤트 표에만
있는 앵커를 놓쳤다(`0x342DC`). 스캔은 앵커 141개 / 즉치 146곳을 빠짐없이 잡는다.

### 같은 대사의 복사본 — 원문 기억으로 처리한다

같은 대사가 화자 워드 `W` 만 바꿔 여러 앵커에 복사돼 있다. 스테이지 16 의 검 습득
대사는 8벌(줍는 유닛마다 한 벌), 스테이지 13 의 거울 대사는 7벌이다.
워크시트에는 한 벌만 싣고, 빌드가 **원문이 같은 메시지의 번역을 재사용**한다.
같은 문장을 여덟 번 옮겨 적지 않기 위한 것이다.

## 제약 — 체인은 전부 한글이거나 전부 원문이어야 한다

글리프 슬롯(타일 128..191)은 **게임의 가나 폰트 자리**다. 한 메시지가 한글 글리프를
올리면 그 타일에 들어 있던 가나가 사라지므로, 같은 체인의 남은 일본어 메시지는
그 타일을 가나로 읽어 깨진다.

그래서 빌드는 체인 단위로 전부 아니면 전무다(`build_chains` 의 `all(kos)`).
번역이 덜 찬 체인은 원문 그대로 두고 로그에 적는다. 원문 기억이 다른 스테이지의
체인 일부만 채우는 일이 실제로 생겼고(`0x335F0` 1/8 등), 그대로 뒀으면 깨졌다.

### 같은 이유로 스테이지 단위로 옮긴다

한 전투 안에서 한글 대사가 한 번 나오면 타일 128..191 은 한글이 된 채 남는다.
그 전투의 다른 일본어 대사·메뉴·유닛 상태창은 게임이 폰트를 다시 올릴 때까지
깨져 보인다. 즉 **한 스테이지의 대사를 다 옮겨야 그 스테이지가 깨끗하다.**

최종본에서는 전부 한글이 되므로 사라지는 문제다. 중간 상태가 확인을 방해할 정도면
`$5F60` 진입부(`0x5FD4` 의 `lea $62BC, a2` 6바이트)에 훅을 걸어 "가나 코드가 섞인
문자열을 그리기 전에 원본 가나 64타일을 복원" 하는 방법이 있다. 원본 폰트는 우리가
가진 VRAM 덤프에 그대로 들어 있다(`FROM_VRAM` 이 이미 그 덤프에서 글리프를 꺼낸다).
필요해지면 그때 한다 — 지금은 한 번에 하나만 바꾼다.

## UI 텍스트 — 문자열이 자기 글리프를 들고 다니게 했다

UI 텍스트는 예외 없이 `lea <문자열>, a1` + `jsr $5F60` 으로 그려진다. 그리기 지점이
150곳이라 지점마다 훅을 걸 수는 없다. 그래서 **문자열 쪽에 글리프를 붙였다.**

훅은 `$5F60` 의 문자열 루프 직전 한 곳(`0x5FD4` 의 `lea $62BC.l, a2`)이면 전부 걸린다.

```
문자열 앞머리  [0x01][k]              k 번째 글리프 기록을 올려라
글리프 기록    [타일][N][ID x N]      UITBL + k*128
```

두 바이트만 붙이는 **간접** 방식인 이유: 클래스명 같은 표는 `lsl.w #4` 로 색인해
엔트리가 16바이트로 고정이다. 글리프 목록을 문자열에 직접 담으면 넘친다.

마커 `0x01` 은 본문 코드(0x7F..0xA0/0xE0..0xFD)·이름 코드(0x0E..0x13)·ASCII·줄바꿈과
겹치지 않는 값이다. 대사 본문도 이 훅을 지나가지만(렌더러가 같다) 첫 바이트가 본문
코드라 절대 0x01 이 아니다 — 빌드가 매번 확인한다.

`k` 는 범위를 검사한다. 아직 번역하지 않은 원본 문자열이 우연히 `0x01` 로 시작하면
엉뚱한 기록을 읽어 VRAM 을 망가뜨린다. 범위 밖이면 a1 을 건드리지 않고 나가므로
원본과 완전히 같게 동작한다.

### 배정 방식은 "한 화면에 몇 개가 보이는가" 로 갈린다

```
positional  한 번에 하나만 보이는 표 — 클래스명 (그리기 11곳, 어디에도 루프 없음)
            엔트리마다 기록을 따로 갖고 k 번째 칸은 항상 코드 UI_CODES[k]
            타일 198..220 / 저바이트 코드 0x02..0x0C, 0x14..0x1F 23개
shared      여러 줄이 동시에 보이는 표 — 마법·아이템 (목록을 루프로 그린다)
            표 전체의 어휘 합집합을 한 기록에 담고 모든 엔트리가 공유한다
            줄마다 다시 올려도 결과가 같으므로 순서에 안 깨진다
            마법 31자 + 아이템 26자 = 본문 슬롯 57/64
```

클래스명을 shared 로 하려면 어휘가 100자를 넘어 코드가 모자란다. 반대로 마법을
positional 로 하면 목록의 앞줄이 뒷줄 글리프로 덮인다. 그래서 표마다 다르다.

**원본 표는 건드리지 않는다.** `lea` 즉치만 우리 표로 돌린다(클래스 11곳, 마법 1곳,
아이템 2곳). 번역이 없는 엔트리는 원본 16바이트를 그대로 복사해 넣는다 — 우리 표가
원본을 완전히 대신하므로 빈 칸을 남기면 그 엔트리가 사라진다.

### 이 방식의 부수 효과 — 스스로 낫는다

문자열이 자기 글리프를 들고 오므로, 대사가 타일 128..191 을 한글로 덮은 뒤에 메뉴를
열어도 메뉴 문자열이 자기 글리프를 다시 올린다. **번역한 것끼리는 서로 안 깨진다.**
아직 일본어인 것만 깨진다.

### 창 서술자 — 두 종류가 있고 네 번째 워드가 가른다

세이브/로드/아이템 없음 같은 단문은 `lea` 로 오지 않는다. **창 레코드**가 32비트
포인터로 물고 있다. 레코드 25개를 전수 확인해 형식을 확정했다.

```
창 레코드   [폭][높이][0xC000][종류][32비트 포인터]
종류 4      텍스트   포인터+0 = [x][y],  포인터+4 부터 문자열
종류 5      타일맵   포인터+4 = 타일 베이스, +8 부터 $5CDC 서술자
```

종류 4 열 개가 전부 깨끗한 일본어로 풀리므로 확정이다. 포인터만 우리 레코드로
돌리면 되고, `[x][y]` 두 워드는 원본을 그대로 복사한다.

### 메뉴는 문자열이 아니다 — 그리고 깨지지 않는다

유닛 명령 메뉴는 종류 5, 즉 타일 번호를 격자로 늘어놓은 네임테이블 조각이다.
`$5CDC` 가 해석한다.

```
바이트 < 0xFA   타일 = 베이스 + 바이트,  d5(뒤집기) OR, $9126 XOR
0xFA..0xFD      뒤집기 없음 / 가로 / 세로 / 양쪽
0xFE nn         다음 바이트를 nn 번 반복
0xFF            끝
```

**타일 베이스가 전부 0x100 이상이다** (메뉴 0x520 = 타일 1312, 그 밖 0x500/0x1C0).
베이스 0x8000(타일 0)인 둘은 창 테두리라 타일 110~118 만 쓴다. 즉 메뉴는 폰트 타일
0..255 를 건드리지 않으므로 **우리 한글 업로드에 깨지지 않는다.** 실측으로 판정하기
애매했던 것을 정적으로 확정했다.

뒤집어 말하면 메뉴 글자는 폰트가 아니라 **미리 그려둔 그래픽**이다.

## 메뉴 한글화 완료 — 풀을 다시 굽고 서술자를 다시 썼다

`tools/menu.py`. 전투 중 메뉴 7개가 한글로 나온다. **실기 확인 완료.**

### 리소스 표 `0x3A400` — 그래픽은 인덱스로 불러온다

메뉴 글리프가 어디서 오는지는 VRAM 주소를 거꾸로 따라가 찾았다.

```
0053B4  그래픽 로드 진입   d1 = 리소스 번호, d2 = VRAM 주소
0058E2  lea $3A400, a0 / a0 = (a0, d1*4)     <- 32비트 포인터 표
0053C2  cmpi.w #1,(a1)+   첫 워드로 코덱 분기
          1 -> 0x53D8 (니블 RLE, 그 안에 원시 복사 경로가 있다)
          그밖 -> 0x54AC (비트플레인)
0006F38  move.w #$7D,d1 / move.w #$A000,d2   <- 전투 메뉴 풀
```

**리소스 0x7D 는 압축이 아니다.** `0x5D7B6` 의 헤더가 `0001 FC 00` 이고
`0x53D8` 의 `d3 == 0` 경로(`0x5494`)가 32바이트씩 그대로 복사한다.

```
비압축 형식   [00 01][타일수 N][00][4bpp 타일 32B x N]      N <= 255
리소스 0x7D   롬 0x5D7BA, 252타일 -> VRAM 0xA000 (타일 1280)
```

VRAM 덤프의 타일 1280..1531 과 롬 바이트가 **전부 일치**해 확정이다. 압축 코덱을
역설계할 필요가 없었다 — 우리가 쓸 형식이 이미 게임 안에 있었다.

### 풀은 8px 열 단위로 중복 제거된 텍스트 띠다

한자는 16px(2열), 가나는 8px(1열)이고 서술자가 필요한 열만 골라 붙인다.
`データ` 의 `ー` 는 `ロード` 의 것을 **재사용**한다.

그래서 "글자 하나를 한글로 바꾼다" 는 발상이 통하지 않는다. `動` 을 `동` 으로
바꾸면 `手動`·`半自動` 까지 같이 바뀌고, 장음부호는 1:1 대응이 아예 없다.

대신 **풀과 서술자를 둘 다 다시 쓴다.** 서술자가 임의의 타일 번호를 임의의 칸에
놓으므로 한글 음절(16x16 = 타일 4개)을 풀 어디에 두든 된다. **인접 조건이 없어서**
조각난 빈 자리를 그대로 쓸 수 있다.

### 손대지 않는 것을 고정한다

```
서술자 8개 중 7개 재작성       03086E 03087C 0309DC 030AAA 030B3C 030B72 030F9E
030A1A 는 그대로              문맥 미확정 — 이 풀로 렌더하면 가운데 줄이 `件ブ` 로 깨진다
BGM / ON / OFF 는 원본 픽셀    영어 라벨은 번역하지 않는다는 기존 결정
미참조 오프셋 21개도 고정      `ロード` `セーブ` 열이 거기 있다 (서술자 아닌 경로)
```

`0xA000` 에는 리소스가 여러 개 번갈아 올라온다(`0x7D` 전투 / `0xB1` `0xB2` `0xB3`
압축). 같은 타일 번호가 문맥마다 다른 그림이라는 뜻이고, `030A1A` 가 다른 풀과
짝일 가능성이 여기서 나온다. `d4 = 0x850A` 같은 즉치로 그리는 코드(0xEFE0 대역,
숫자 출력)도 그 다른 풀을 전제한다 — 전투 화면에서 그 자리는 `魔法` 이다.

"안 쓰는 것 같다" 로 타일을 덮어써서 스테이지 번호 `1` 을 깨뜨린 적이 있다.
그래서 미참조 타일까지 보험으로 고정한다. 비용은 21타일이고 예산은 남았다.

### 남은 메뉴 — 프롤로그 풀(타일 448)

`030FEE` `03104C` `0310A6` `038800` 넷은 베이스 `0x81C0`(타일 448)이고 리소스
`0x81` 에서 온다. **압축**이라 replace 하려면 원본을 풀어 우리 비압축 블록으로
다시 굽고 리소스 표 엔트리를 돌려야 한다(형식은 위에 있으므로 경로는 뚫려 있다).
`0x81` 은 `0x18C9C`(프롤로그 렌더러 대역)가 올린다.

## 실측에서 드러난 결함 — 훅을 렌더러 안 한 곳으로 모았다

메뉴를 확인하다 두 화면이 깨진 것이 나왔다. 둘 다 원인이 같다 — **번역문을 그리는
경로가 하나가 아니었다.**

### 전투 중 승리조건 창

프롤로그 화면 문자열은 첫 문자열만 `[0xFE][N][ID x N]` 헤더를 달고, 프롤로그
렌더러의 첫 draw(`0x18D12`)에 걸린 훅이 화면 합집합을 올렸다. 그런데 같은 표
`0x3962E` 를 **전투 중 승리조건 창(`0x10C36`)이 또 읽는다.** 그 경로에는 훅이 없으니
헤더 바이트가 글자로 찍히고, 본문 슬롯에는 앞 대사의 글리프가 남아 있었다.

고친 방법은 UI 텍스트와 같은 방식으로 **통일**한 것이다.

```
프롤로그 3문자열   [0xFE] 헤더 -> [0x01][k] (UI 마커) + 화면 단위 공유 기록 하나
훅                0x18D12 (경로 하나) -> 0x5FD4 ($5F60 안, 모든 경로)
기록 엔트리        128B -> 136B   (합집합 64자 = 2 + 128B 가 들어가야 한다)
```

`0x18D12` 훅은 승리/패배 라벨 업로드 때문에 남겨 뒀다. 마커가 `0xFE` 가 아니면
글리프 부분을 건너뛰고 라벨만 올린다.

**교훈: 그리기 지점에 훅을 걸면 경로를 전부 찾아야 한다.** 렌더러 안에 한 번 걸면
찾을 필요가 없다. UI 텍스트에서 이미 얻은 결론을 프롤로그 쪽에 되먹이지 않아서
생긴 결함이다. 같은 문자열을 두 화면이 읽는다는 것도 그때는 몰랐다.

### 창 머리글은 조건문보다 먼저 그려진다

`しょうり` / `はいぼく`(`0x30A92`)는 표도 창 레코드도 아닌 **`lea` 로 오는 낱개
문자열**이고, 조건문보다 먼저 그려진다. 조건문이 본문 슬롯(128..191)에 한글을
올리므로 머리글이 그 범위를 쓰면 이미 그린 글자가 조건문 글리프로 변한다.
그래서 팝업 칸(206..220)에 배정했다 — 팝업과 이 창은 동시에 뜨지 않는다.

`ui.tsv` 에 `str` 필드를 추가했다(키 = 롬 주소, `lea` 즉치를 전수 치환).

### 세이브 확인 창

`データをセーブしました / ゲームをつづけますか?` 는 남은 일본어라 가나 타일이
한글로 덮인 뒤 깨져 보였다. 번역해서 자기 글리프를 들고 오게 했다.

- 창 레코드가 `0x000282` — 롬 앞쪽에 있어서 포인터 범위 assert 를 풀었다
- `Yes` / `No` 를 살리려고 `ASCII_OK` 에 소문자를 넣었다. 게임 ASCII 폰트는
  타일 0..95 = 코드 `0x20..0x7F` 라 소문자가 원래 다 있다

빌드가 문자열을 되읽어 검증하기 쉬워졌다 — `[0x01][k]` 기록에서 타일 배정을 읽고
`$62BC` 로 코드를 되돌리면 화면에 찍힐 문자가 그대로 나온다. 실기 전에 걸러진다.

## 유닛 상태창 — 이름 + 라벨

패널 하나에 **이름·클래스명·라벨이 동시에** 보인다. 그래서 이 작업은 번역이 아니라
**타일 배정** 문제였다.

### 라벨 `しきはんい` / `しゅうせい`

`0x31548` 대역에 짧은 문자열이 `0xFF` 로 끊겨 죽 늘어서 있다(`HP` `MP` `AT` `DF`
`MV` `LV` `しきはんい` `しゅうせい` `A+` `D+` `ITEM` `Pts`). 표가 아니라 **낱개마다
`lea` 즉치가 따로 있다** — 상태창 라벨 루틴 `0x128E4` 가 그 둘을 `jsr $5F60` 으로
그린다. 그래서 `ui.tsv` 의 `str` 필드로 그대로 처리된다.

`A+` `D+` 는 `$5F7A`(다른 문자열 루틴)로 그려지고 영어라 손대지 않는다.
`じどうせんたく`(`0x31586`)는 롬 어디서도 참조하지 않는다 — 죽은 문자열이다.

### 전투 화면 타일 배분 (타일 192..255)

강제 표시로 전직 팝업을 띄웠더니 상태창의 `지휘범위 수정` 이 `인지` 로 변했다.
팝업 글리프(206..)가 라벨 타일(206..211)을 덮은 것이다. 팝업은 상태창과 **같이 뜨는**
것이므로 "다시 그리면 낫는다" 로 넘길 문제가 아니었다.

코드 페이지가 있으니 구간을 제대로 갈랐다. 64칸(192..255)을 이렇게 쓴다.

```
192..197  이름 6칸            코드 0x0E..0x13 (위치)
198..205  클래스명 8칸         코드 0x02..0x09 (위치)
206..220  팝업 단문 15칸       코드 0x0A..0x0C / 0x14..0x1F
221..244  용병 클래스 어휘 24   페이지 1  (팝업과 안 겹치게 212 -> 221 로 물림)
245..250  상태창 라벨 6        페이지 5
251..255  여유
```

빌드가 같은 화면 요소들의 구간 겹침을 재검증한다(이름·클래스·팝업·용병·라벨).

### 슬롯 배정 — 두 번 실패하고 전용 페이지로

저바이트 코드는 이미 다 찼다(이름 6 + 클래스 8 + 팝업 15 = 23개). 새 타일을 쓰려면
새 코드가 필요한데 남은 바이트 값이 없다(가나 `0xA1..0xDF` 는 남은 일본어 때문에
건드릴 수 없다).

그래서 **본문 슬롯의 남는 뒤쪽**을 썼다 — 마법·아이템 공유 어휘가 64칸 중 57칸만
쓰므로 그 뒤 6칸(타일 185..190)이 비어 있었다. **실기에서 깨졌다.**

```
ル 코드 D9 -> 타일 185 = 우리 '지'      지휘관 이름판이 ヴォ지コフ 로
レ 코드 DA -> 타일 186 = 우리 '휘'                    휘ディ수 로
ン 코드 DD -> 타일 189 = 우리 '수'
```

**본문 슬롯은 곧 게임의 가나 폰트 자리다.** 상태창과 같은 화면에 있는 지휘관
이름판(출전 준비 화면 위쪽)이 원본 카타카나라 그 타일을 읽는다. "비어 있다" 는
판단이 우리 배정 안에서만 참이었다.

고친 배정은 **팝업 칸(타일 206..211)** 이다. 두 라벨이 기록 하나를 공유한다.

```
지휘범위 + 수정 = 음절 6개   타일 206..211   코드 UI_CODES[8..13]
```

팝업과는 겹친다(팝업도 206 부터 쓴다). 상태창이 떠 있는 채로 팝업이 나오면 라벨이
잠깐 변하고, 패널을 다시 그리면 낫는다. 남은 일본어가 영구히 깨지는 것보다 낫다.

**교훈: "같이 보이는 것" 에는 남은 일본어도 든다.** 본문 슬롯 128..191 을 쓰는
문자열은 같은 화면의 원문 가나를 반드시 깨뜨린다.

### 이름 — 목록 창은 건드리지 않는다

이름표 `0x2AE64` 를 읽는 `lea` 가 18곳이다. 그중 **유닛 상태창 3변형**
(`0x1257C` `0x1260E` `0x126A4` — 이름 -> 클래스명 -> LV 를 잇달아 그리는 같은 모양)
만 우리 표로 돌렸다.

나머지 14곳은 원문 그대로다. 그중 **출전 준비 화면 위쪽의 지휘관 이름판**은 여러
개가 동시에 보인다 — 우리 방식은 이름마다 타일 192..197 을 돌려쓰므로 마지막
이름으로 다 변한다. 이름 하나당 6칸 x 이름판 수만큼 슬롯이 필요하고 지금 예산으로는
안 된다. (이름을 그리는 코드에 루프는 없다. 자리마다 단일 draw 이고 화면 쪽에서
여러 번 부르는 구조여서, 코드만 보고 "루프인가" 로는 판정할 수 없었다.)

이름표 엔트리에 `[0x01][기록번호]` 를 달았다(16바이트에 2 + 6칸 + 종료자 = 9). 대사
이름판은 `0x157C8` 훅이 `$E82A` 로 올리지만 상태창은 그 훅을 지나지 않는다. 마커를
달아 두니 `$5F60` 안의 훅이 **경로와 무관하게** 올린다 — 훅을 한 곳으로 모은 것이
바로 여기서 값을 했다.

기록이 78개 늘어 표가 27KB 가 됐다. 글리프 테이블을 `0x88000` -> `0x90000` 으로
옮겼다(`place()` 가 겹침을 잡아 준다).

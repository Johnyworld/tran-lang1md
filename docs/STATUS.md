# 랑그릿사 (MD) 한글화 — 현황

## 대상 롬

```
Langrisser.md   524288 bytes (4Mbit)
SHA1  cc67c5a3b91e706b495eb561a95a038fff72b5da
MD5   4759f8db3ee29d85f7087886d813c04b
헤더  (C)T-25 1991.JAN / ラングリッサー / GM T-25103-00 / J
SRAM  있음 (0x01B0 "RA")
```

## 확정된 사실

- **평문 SJIS 텍스트 없음.** 롬 전체를 SJIS 2바이트 시퀀스로 스캔했으나 유효한 일본어 문장이
  헤더의 `ラングリッサー` 하나뿐. → 자체 코드 테이블 또는 압축.
- **폰트는 정적으로 못 찾음.** 두 가지 탐지를 돌렸고 둘 다 실패:
  - 1bpp 해석: 저엔트로피 후보 `0x2C000` 대역 → 글리프 아님(다른 테이블 데이터)
  - 4bpp 2색 해석: `0x5D800` / `0x5E800` / `0x61000` 이 니블 {0xD, 0xF}만 사용해 후보로
    잡혔으나 타일 렌더 결과 글리프 아님
- 16KB 블록 엔트로피가 전 구간 6.0~6.8로 균일 → **그래픽·텍스트 모두 압축 저장**으로 판단.

결론: 정적 분석으로는 진행 불가. 런타임 VRAM 덤프로 폰트 실물을 확보한 뒤,
그 비트패턴을 키로 롬 내 압축 스트림과 압축 해제 루틴을 역추적한다.

## VRAM 해석 결과 (해결됨)

덤프: `work/Mega Drive/Langrisser-vdp-vram-*.bin` (64KB, 프롤로그 화면, 4장 모두 동일)

ares Export 가 무반응이던 원인은 `Paths → Debugging` 미설정. 설정 후 정상 동작.

### 폰트 두 종류

**8x8 ASCII** — 타일 `0..95`, `타일 = 문자코드 - 0x20` (0x20..0x7F).
`PLAYER` / `ENEMY` / 숫자용.

**8x16 가나** — 세로로 붙은 두 타일이 한 글자.

| | |
|---|---|
| 아래 타일 (가나 본체) | 카타카나 `타일 = JIS X 0201 - 0x20` → `0xA1..0xDF` = `129..191` |
| | 히라가나 `타일 = JIS X 0201 + 0x20` → `0xA1..0xDF` = `193..255` |
| 위 타일 (탁점) | `101` = 공백, `106` = ゛, `107` = ゜ |

즉 `げ` = 아래 `け`(217) + 위 `゛`(106). 탁점을 별도 타일로 얹는 구조라
가나 본체는 71자만 있으면 된다.

### 화면 구조

```
네임테이블  VRAM 0xC000, 64칸, 행 피치 0x80
본문 영역   3..34 칸 (32칸), 행 5·7·9·11·13
행 피치     타일 2행 = 16px
勝利/敗北   2x2 타일 한자 그래픽 (타일 522..541), 폰트 아님
```

`tools/decode_screen.py` 로 화면 텍스트 전체 복원 검증 완료 —
스크린샷과 한 글자도 틀리지 않음.

### 한글화 관점에서의 함의

- **세로는 공짜.** 게임이 이미 16px 행 피치에 타일 2행을 쓰므로 한글 16x16 이 그대로 맞는다.
  위 타일이 지금은 탁점 전용이지만 한글에선 글리프 상반부로 쓰면 된다.
- **가로가 문제.** 한글 1음절 = 가로 2칸 → 한 줄 32칸 = **한글 16자**.
  원문은 한 줄 32가나이므로 정보량이 거의 반으로 준다. 줄 수를 늘리거나
  본문 영역을 넓히는 조정이 필요할 수 있다.
- 한글 1음절 = 2x2 타일 4개. 위/아래 타일 행에 모두 써야 하므로
  현재 "위 행은 탁점만" 가정으로 짜인 렌더러 수정이 필요하다.

### 롬 내 폰트 위치 (해결됨)

VRAM 폰트 타일을 1bpp(잉크 = 색상 15)로 변환해 롬에서 검색 → **`0x3B09A`~`0x3B970` 확정**.
압축이 아니라 **1bpp 저장**이었다. 초기 4bpp 2색 탐지기가 놓친 이유가 이것.

저장 형식은 단순 배열이 아니다. 대부분 글리프는 8바이트 stride 지만,
빈 행이 있는 글자(`a` `c` `e` `g` 등)는 **6바이트로 줄어 있다** — 빈 행을 잘라낸 가변 길이.
어느 행이 잘렸는지 알려주는 헤더는 글리프 옆에 없으므로 별도 테이블이 있을 것으로 추정.
오프셋이 8바이트 정렬도 아니다(예: `A` = `0x3B224`, mod 8 = 4).

폰트를 가리키는 32비트 절대 포인터는 롬에 없다.
`0x1C820` 이 후보로 잡혔으나 `move.w #$0003, $B09A.w` 의 피연산자가 우연히 이어진 오탐.
뱅크 오프셋 또는 테이블 경유 참조로 보인다.

### 텍스트 인코딩 (해결됨)

**텍스트는 압축이 아니라 평문이었다.** 초기 검색이 빗나간 이유는 두 가지 —
탁점이 별도 바이트로 뒤에 붙어 문자열이 끊겼고, 카타카나가 별도 모드였다.

```
0x0D        줄바꿈
0x20..0x7D  ASCII 그대로 (0x20 = 공백)
0x7E        카타카나 모드 토글 (고유명사를 감싼다)
0xA1..0xDD  JIS X 0201 가나 — 기본 히라가나, 토글 중이면 카타카나
0xDE        탁점  ゛ (직전 글자에 결합)
0xDF        반탁점 ゜ (직전 글자에 결합)
0xFF        메시지 종료 (뒤에 0x00 이 따라오는 경우가 많다)
```

히라가나 바이트가 JIS X 0201 카타카나 코드와 그대로 같다.
카타카나는 같은 바이트를 `0x7E` 모드 안에서 쓴다. 폰트 타일이
히라가나/카타카나 두 벌로 나뉘어 있던 것과 대응된다.

검증: 프롤로그 블록을 디코드해 스크린샷과 일치 확인.

### 대본 위치와 규모

대본 블록 탐지는 검증된 블록의 바이트 알파벳을 기준으로 슬라이딩 윈도우
(64바이트 중 92% 이상)로 수행. `work/script_blocks.txt` 에 88개 블록 기록.
주 대본은 `0x33000`~`0x39A00` 에 집중.

```
메시지    896개
원본      28,545 bytes
일본어    26,345자
```

`tools/script.py` → `work/script.json`, `work/script.tsv`(번역 워크시트).

## 주소지정 방식 (해결됨)

### 포인터 테이블은 20스테이지 메타데이터 전용

| 테이블 | 엔트리 | 내용 |
|---|---|---|
| `0x38A38` | 20 | 스테이지 이름 |
| `0x38BF2` | 20 | 스테이지 프롤로그 |
| `0x3962E` | 20 | 승리/패배 조건 |
| `0x2087C` | 14 | (미분류) |
| `0x3A322` | 11 | (미분류) |

### 본편 대사에는 포인터 테이블이 없다

delta 수열 지문으로 (2/4바이트 값) × (stride 2/4/6/8) 조합을 전수 탐색 → **전부 0건**.
탐색 코드는 알려진 테이블 `0x38BF2` 를 정확히 찾아내므로 코드 결함이 아니다.

실제 방식은 **68000 코드 안의 즉치(immediate)** 였다.

```
21 FC 00 03 35 4A E8 32   =   move.l #$0003354A, $E82C.w
```

`tools/refs.py` → `work/refs.json`

```
대본을 가리키는 코드 즉치   212개
  move.l #imm,(d16).w      157   (목적지 대부분 $E82C = 메시지 포인터 RAM 변수)
  lea imm.l,a0/a1/a2        54
  move.l #imm,(xxx).l        1
서로 다른 타겟 주소         153개
메시지 시작에 정확히 일치    97개
```

메시지는 `0xFF` 구분자로 빽빽하게 붙어 있고 사이에 이벤트 명령 바이트가 없다
(간격이 거의 전부 정확히 1바이트). 즉치 153개 < 메시지 896개 이므로,
즉치는 **대화의 시작점**을 가리키고 이후 메시지는 순차로 진행된다.
대화가 어디서 끝나는지(`0xFF 0x00` 가설은 기각 — 앵커 앞이 대부분 `0xFF` 단독)는
아직 규명되지 않았으나, **아래 재삽입 전략에서는 알 필요가 없다.**

### 재삽입 전략

in-place 로 고치면 길이 변화가 뒤쪽 전부를 밀어내므로, 대신
**대본 전체를 확장 영역(512KB → 1MB)으로 이설하고 즉치 212개를 재계산**한다.
메시지 순서와 구분자만 보존하면 순차 진행 동작이 그대로 유지되므로
대화 종료 조건을 몰라도 안전하다. 길이 제약도 사라진다.

**알려진 결함**: 블록 시작 -64 지점부터 스캔하므로 각 윈도우의 첫 메시지가
경계에서 어긋날 수 있다. 어긋나면 앞쪽 `0x7E` 를 놓쳐 히라가나/카타카나가
뒤바뀐 채 디코드된다. `work/refs.json` 의 타겟 주소를 앵커로 삼아
재분할하면 해결된다.

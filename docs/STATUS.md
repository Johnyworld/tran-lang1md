# 랑그릿사 (MD) 한글화 — 현황

## 대상 롬

```
Langrisser.md   524288 bytes (4Mbit)
SHA1  cc67c5a3b91e706b495eb561a95a038fff72b5da
MD5   4759f8db3ee29d85f7087886d813c04b
헤더  (C)T-25 1991.JAN / ラングリッサー / GM T-25103-00 / J
SRAM  있음 (0x01B0 "RA")
```

## 확정된 사실

- **평문 SJIS 텍스트 없음.** 롬 전체를 SJIS 2바이트 시퀀스로 스캔했으나 유효한 일본어 문장이
  헤더의 `ラングリッサー` 하나뿐. → 자체 코드 테이블 또는 압축.
- **폰트는 정적으로 못 찾음.** 두 가지 탐지를 돌렸고 둘 다 실패:
  - 1bpp 해석: 저엔트로피 후보 `0x2C000` 대역 → 글리프 아님(다른 테이블 데이터)
  - 4bpp 2색 해석: `0x5D800` / `0x5E800` / `0x61000` 이 니블 {0xD, 0xF}만 사용해 후보로
    잡혔으나 타일 렌더 결과 글리프 아님
- 16KB 블록 엔트로피가 전 구간 6.0~6.8로 균일 → **그래픽·텍스트 모두 압축 저장**으로 판단.

결론: 정적 분석으로는 진행 불가. 런타임 VRAM 덤프로 폰트 실물을 확보한 뒤,
그 비트패턴을 키로 롬 내 압축 스트림과 압축 해제 루틴을 역추적한다.

## VRAM 해석 결과 (해결됨)

덤프: `work/Mega Drive/Langrisser-vdp-vram-*.bin` (64KB, 프롤로그 화면, 4장 모두 동일)

ares Export 가 무반응이던 원인은 `Paths → Debugging` 미설정. 설정 후 정상 동작.

### 폰트 두 종류

**8x8 ASCII** — 타일 `0..95`, `타일 = 문자코드 - 0x20` (0x20..0x7F).
`PLAYER` / `ENEMY` / 숫자용.

**8x16 가나** — 세로로 붙은 두 타일이 한 글자.

| | |
|---|---|
| 아래 타일 (가나 본체) | 카타카나 `타일 = JIS X 0201 - 0x20` → `0xA1..0xDF` = `129..191` |
| | 히라가나 `타일 = JIS X 0201 + 0x20` → `0xA1..0xDF` = `193..255` |
| 위 타일 (탁점) | `101` = 공백, `106` = ゛, `107` = ゜ |

즉 `げ` = 아래 `け`(217) + 위 `゛`(106). 탁점을 별도 타일로 얹는 구조라
가나 본체는 71자만 있으면 된다.

### 화면 구조

```

본문 영역   3..34 칸 (32칸), 행 5·7·9·11·13
행 피치     타일 2행 = 16px
勝利/敗北   2x2 타일 한자 그래픽 (타일 522..541), 폰트 아님
```

스크린샷과 한 글자도 틀리지 않음.

### 한글화 관점에서의 함의

- **세로는 공짜.** 게임이 이미 16px 행 피치에 타일 2행을 쓰므로 한글 16x16 이 그대로 맞는다.
  위 타일이 지금은 탁점 전용이지만 한글에선 글리프 상반부로 쓰면 된다.
- **가로가 문제.** 한글 1음절 = 가로 2칸 → 한 줄 32칸 = **한글 16자**.
  원문은 한 줄 32가나이므로 정보량이 거의 반으로 준다. 줄 수를 늘리거나
  본문 영역을 넓히는 조정이 필요할 수 있다.
- 한글 1음절 = 2x2 타일 4개. 위/아래 타일 행에 모두 써야 하므로
  현재 "위 행은 탁점만" 가정으로 짜인 렌더러 수정이 필요하다.

### 롬 내 폰트 위치 (해결됨)

VRAM 폰트 타일을 1bpp(잉크 = 색상 15)로 변환해 롬에서 검색 → **`0x3B09A`~`0x3B970` 확정**.
압축이 아니라 **1bpp 저장**이었다. 초기 4bpp 2색 탐지기가 놓친 이유가 이것.

저장 형식은 단순 배열이 아니다. 대부분 글리프는 8바이트 stride 지만,
빈 행이 있는 글자(`a` `c` `e` `g` 등)는 **6바이트로 줄어 있다** — 빈 행을 잘라낸 가변 길이.
어느 행이 잘렸는지 알려주는 헤더는 글리프 옆에 없으므로 별도 테이블이 있을 것으로 추정.
오프셋이 8바이트 정렬도 아니다(예: `A` = `0x3B224`, mod 8 = 4).

폰트를 가리키는 32비트 절대 포인터는 롬에 없다.
`0x1C820` 이 후보로 잡혔으나 `move.w #$0003, $B09A.w` 의 피연산자가 우연히 이어진 오탐.
뱅크 오프셋 또는 테이블 경유 참조로 보인다.

### 텍스트 인코딩 (해결됨)

**텍스트는 압축이 아니라 평문이었다.** 초기 검색이 빗나간 이유는 두 가지 —
탁점이 별도 바이트로 뒤에 붙어 문자열이 끊겼고, 카타카나가 별도 모드였다.

```
0x0D        줄바꿈
0x20..0x7D  ASCII 그대로 (0x20 = 공백)
0x7E        카타카나 모드 토글 (고유명사를 감싼다)
0xA1..0xDD  JIS X 0201 가나 — 기본 히라가나, 토글 중이면 카타카나
0xDE        탁점  ゛ (직전 글자에 결합)
0xDF        반탁점 ゜ (직전 글자에 결합)
0xFF        메시지 종료 (뒤에 0x00 이 따라오는 경우가 많다)
```

히라가나 바이트가 JIS X 0201 카타카나 코드와 그대로 같다.
카타카나는 같은 바이트를 `0x7E` 모드 안에서 쓴다. 폰트 타일이
히라가나/카타카나 두 벌로 나뉘어 있던 것과 대응된다.

검증: 프롤로그 블록을 디코드해 스크린샷과 일치 확인.

### 대본 위치와 규모

대본 블록 탐지는 검증된 블록의 바이트 알파벳을 기준으로 슬라이딩 윈도우
(64바이트 중 92% 이상)로 수행. `work/script_blocks.txt` 에 88개 블록 기록.
주 대본은 `0x33000`~`0x39A00` 에 집중.

```

```

`tools/script.py` → `work/script.json`, `work/script.tsv`(번역 워크시트).

## 주소지정 방식 (해결됨)

### 포인터 테이블은 20스테이지 메타데이터 전용

| 테이블 | 엔트리 | 내용 |
|---|---|---|
| `0x38A38` | 20 | 스테이지 이름 |
| `0x38BF2` | 20 | 스테이지 프롤로그 |
| `0x3962E` | 20 | 승리/패배 조건 |
| `0x2087C` | 14 | (미분류) |
| `0x3A322` | 11 | (미분류) |

### 본편 대사에는 포인터 테이블이 없다

delta 수열 지문으로 (2/4바이트 값) × (stride 2/4/6/8) 조합을 전수 탐색 → **전부 0건**.
탐색 코드는 알려진 테이블 `0x38BF2` 를 정확히 찾아내므로 코드 결함이 아니다.

실제 방식은 **68000 코드 안의 즉치(immediate)** 였다.

```
21 FC 00 03 35 4A E8 32   =   move.l #$0003354A, $E82C.w
```

`tools/refs.py` → `work/refs.json`

```
대본을 가리키는 코드 즉치   212개
  move.l #imm,(d16).w      157   (목적지 대부분 $E82C = 메시지 포인터 RAM 변수)
  lea imm.l,a0/a1/a2        54
  move.l #imm,(xxx).l        1
서로 다른 타겟 주소         153개
메시지 시작에 정확히 일치    97개
```

메시지는 `0xFF` 구분자로 빽빽하게 붙어 있고 사이에 이벤트 명령 바이트가 없다
(간격이 거의 전부 정확히 1바이트). 즉치 153개 < 메시지 896개 이므로,
즉치는 **대화의 시작점**을 가리키고 이후 메시지는 순차로 진행된다.
대화가 어디서 끝나는지(`0xFF 0x00` 가설은 기각 — 앵커 앞이 대부분 `0xFF` 단독)는
아직 규명되지 않았으나, **아래 재삽입 전략에서는 알 필요가 없다.**

### 재삽입 전략

in-place 로 고치면 길이 변화가 뒤쪽 전부를 밀어내므로, 대신
**대본 전체를 확장 영역(512KB → 1MB)으로 이설하고 즉치 212개를 재계산**한다.
메시지 순서와 구분자만 보존하면 순차 진행 동작이 그대로 유지되므로
대화 종료 조건을 몰라도 안전하다. 길이 제약도 사라진다.

## 렌더러 (해결됨)

### 메시지 인터프리터 `0x1536E`

`$E82C`(기준 포인터) → `$E818`(작업 포인터). 16비트 워드를 읽어 명령을 분기하고
`0xFF30DA` / `0xFF517C` 테이블을 인덱싱한다. 최상위 비트가 선 워드는 종료.

`0x15470` 에 **순차 진행이 코드로 확증**되어 있다 — 메시지를 건너뛸 때
포인터 산술이 아니라 `0xFF` 를 찾아 바이트를 하나씩 훑는다.

```
015470  move.b  (a1)+, d5
015472  cmpi.b  #$FF, d5
015476  bne     $15470
015478  move.b  (a1)+, d5        ; 한 번 더
01547A  cmpi.b  #$FF, d5
01547E  bne     $15478
```

따라서 대본을 이설하고 앵커만 재계산하면 순서·구분자 보존만으로 동작이 유지된다.

### 글리프 렌더러 `0x15576`

상태 변수:

| 주소 | 내용 |
|---|---|
| `$E818` | 작업 포인터 |
| `$E81C` | X (칼럼) |
| `$E81E` | Y (행) |
| `$E820` | 히라가나 모드 플래그 |

동작:

```
01557E  move.b  (a1)+, d6            텍스트 바이트
015580  cmpi.b  #$FF   -> 종료
015588  cmpi.b  #$0D   -> 줄바꿈
015594  eori.w  #$1, $E820           0x7E = 모드 플래그 토글
                                     (코덱의 히라가나 토글과 일치)
줄바꿈:
0155AC  move.w  $AEAA.w, $E81C       X 를 행 시작값으로
0155B4  addi.w  #$A, $E81C           + 10  (좌측 여백)
0155BC  addq.w  #$1, $E81E           Y += 1

글자 출력:
0155C4  move.w  $E81C, d1            d1 = X
0155CA  move.w  $E81E, d2            d2 = Y
0155D0  addq.w  #$1, $E81C           X += 1     <<< 칼럼 전진
0155D6  move.w  #$C000, d3           네임테이블 베이스
0155DA  move.w  #$8000, d4           타일 속성
0155EC  addi.w  #$40, d4             히라가나면 +0x40  <<< 타일 오프셋
0155F4  jsr     $5F2E                타일 1개 출력

탁점:
0155FC  cmpi.b  #$DF  (반탁점)
015602  cmpi.b  #$DE  (탁점)
015608  subq.w  #$1, d2              Y -= 1   <<< 윗줄에 찍는다
01560A  jsr     $5F2E
```

히라가나 `+0x40` 은 앞서 VRAM 에서 관측한 카타카나(129..191) / 히라가나(193..255)
타일 차이 64 와 정확히 일치한다. 탁점의 `Y-1` 도 "위 타일에 얹힌다" 는 관측과 일치.

### 바이트 → 타일 변환 테이블 `$62BC`

`$5EFE` 가 실제 타일을 찍는다. 핵심은 **256바이트 룩업 테이블**이다.

```
005F0C  lea.l   $62BC.l, a2
005F12  move.b  (a2, d6.w), d2      텍스트 바이트 -> 타일 번호
005F1C  or.w    d5, d2
005F1E  or.w    d4, d2              속성 결합 (히라가나면 0x40 이 여기 실림)
005F20  move.w  d1, (a1)+           VDP 주소
005F22  move.w  d2, (a1)+           타일 워드
```

앞서 "타일 = 바이트 + 0x20" 이라고 적은 것은 산술이 아니라 **이 테이블 내용을
관측한 결과**였다. 매핑은 테이블만 고쳐 자유롭게 재정의할 수 있다.

단 엔트리가 `move.b` 라 **타일 번호가 0..255 로 제한된다.** 현재 테이블은
서로 다른 타일 160종을 쓰고 최대값이 189, 미사용 타일 번호가 96개다.

### 타일 예산

```
프롤로그 번역문 고유 음절     53자
필요 타일 (음절당 2x2 = 4)   212개
테이블 미사용 타일            96개   -> 부족
가나 타일(129..189) 회수      61개
안 쓰는 ASCII 타일 회수       ~90개  -> 합계 약 247개, 212 들어감
```

가나 폰트를 덮어쓰므로 **다른 화면의 일본어는 깨진다.** 파이프라인 테스트에는
무해하며, 오히려 전체 게임에 동적 글리프 로딩이 필요한 이유를 실증한다.

MD VRAM 은 2048타일이고 이 화면이 이미 ~600타일을 쓴다. 대사 폰트 경로가
0..255 만 주소지정하므로, 전체 게임 한글화는 **메시지마다 필요한 글리프만
VRAM 에 실시간 업로드**하는 구조가 반드시 필요하다.

### 폰트 저장 형식 (정정)

앞서 "빈 행을 잘라낸 가변 길이" 라고 적었으나 오독이었다. 확정된 글리프 150개의
연속 간격 분포는 **8 이 129곳**, 14 가 8곳, 나머지는 산발적 대형 간격이다.
즉 stride 8 배열이 여러 구간으로 쪼개져 있고 구간 사이에 2바이트가 끼는 구조다.
간격 14 는 중간 글리프를 검색으로 찾지 못한 자리다(빈 글리프이거나
색상 15 기준 1bpp 변환이 일치하지 않은 경우).

이 형식은 더 파지 않는다. 기존 폰트를 고치는 대신 **자체 한글 타일 블록을
따로 업로드**하는 쪽이 형식 의존이 없고 동적 로딩에도 그대로 쓰인다.

### 그래픽 VRAM 업로드 루틴 `0x54AC`

```
0054B2  move.w  #$2700, sr           인터럽트 차단
0054CC  move.l  d0, $C00004.l        VDP 컨트롤 — d1 이 VRAM 주소
0054D4  lea.l   $C00000.l, a6        VDP 데이터 포트
0054E0  tst.b   (a0)+                최상위 비트로 압축/비압축 분기
0054E4  bsr.w   $55B2
0054F4  move.b  (a0)+, d5 / lsl #8 / move.b (a0)+, d5
0054FA  lea.l   (a0, d5.w), a1       16비트 오프셋으로 두 번째 스트림 진입
```

비트플레인 기반 자체 압축 코덱이다. 인자는 `d1` = VRAM 주소, `a1` = 소스.
그래픽이 압축이라던 초기 판단은 이 루틴 기준으로 맞았다(폰트만 1bpp 비압축).

한글 타일은 이 코덱을 역설계하는 대신 **비압축 업로드 루틴을 새로 짜서**
올린다. 형식을 우리가 정하는 쪽이 싸다.

## 부팅 체크섬 검사 (실측 확인)

`0x4630` 에 검사 루틴이 있고 **실제로 작동한다.** 체크섬을 고치지 않은 롬은
빨간 화면으로 죽는다(실측).

```
004630  lea.l   $200.w, a0
004634  sub.l   a0, d0          합산 길이 = 롬끝 - 0x200
004636  asr.l   #$1, d0         워드 개수
004640  add.w   (a0)+, d1       합산 루프
004642  dbra    d2, $4640
004646  dbra    d0, $4640
00464A  tst.w   $18e.w          <<< 헤더 체크섬이 0 이면 비교를 건너뛴다
00464E  beq.b   $465a
004650  lea.l   $18e.w, a0
004654  cmp.w   (a0), d1
004656  bne.w   $4840           불일치 -> 에러 화면
```

`0x18E` 에 `0000` 을 써두면 검사를 아예 건너뛴다(개발용 경로).
**작업 중에는 이 우회를 쓰고 최종 배포 패치에서만 정상 체크섬을 넣는다.**
매 빌드 재계산을 한 번 빠뜨리면 원인 불명의 빨간 화면을 보게 된다.

## 텍스트 파이프라인 실측 검증 (통과)

`tools/build.py` 로 프롤로그 자리에 27바이트 테스트 문자열을 넣고 ares 로 확인.
가정 7개가 모두 화면으로 검증됐다.

| 가정 | 결과 |
|---|---|
| 부팅 시 체크섬 검사 | 있음 — 미수정 롬은 빨간 화면 |
| 메시지 주소 `0x38C42` | 그 화면 맞음 |
| ASCII 경로 `0x20..0x7D` | `KOROM TEST` 정상 |
| 기본 모드 = 카타카나 | `テスト` 정상 |
| `0x7E` = 히라가나 토글 | `てすと` 정상 — 극성 정정이 옳았음 |
| `0xDE` = 앞 글자에 탁점 결합 | `デ` 로 합쳐짐 |
| `0x0D 0x0D` = 한 줄 | 줄 간격 원본과 동일 |

`0x0D` 하나는 `Y += 1`(타일 1행)이고 8x16 글리프는 2행을 쓰므로 한 줄에 두 개가
필요하다. 번역문 삽입 시에도 줄바꿈은 `0x0D 0x0D` 로 넣는다.

메시지를 27바이트로 잘라도 다음 프롤로그(별도 포인터 참조)는 정상 출력됐다.
종료자 뒤 잔여 바이트는 도달 불가임이 확인됐다.

### 한글화 수정 지점

1. **`0x1555D0` `addq.w #$1, $E81C` → `addq.w #$2`**
   한글 1음절 = 가로 2칸. 이 한 명령이 핵심.
2. **`$5F2E`(단일 타일 출력)** — 글리프 집합이 크게 늘어나므로 타일 인덱스
   계산 확장 필요. `d4` 속성 워드에 인덱스가 실린다.
3. **`0x1555B4` `addi.w #$A`** — 줄바꿈 시 좌측 여백. 본문 폭 조정 시 건드린다.
4. **탁점 경로(`0x1555FA`~`0x155616`)를 재활용한다.**
   `Y-1` 위치에 두 번째 타일을 찍는 메커니즘이 이미 있으므로,
   한글 글리프의 상반부를 여기에 그대로 얹으면 된다.
   렌더러를 새로 짜지 않아도 된다는 뜻이다.

4번이 이 프로젝트에서 가장 운이 좋은 부분이다. 게임이 이미
"현재 칸 위에 타일 하나 더 찍기" 경로를 갖고 있다.

**알려진 결함**: 앵커 없는 블록은 블록 시작 직전 `0xFF` 뒤에서 스캔하므로
정렬이 보장되지 않는다. 앵커 검증된 메시지는 `anchor: true` 로 표시된다
(1026개 중 165개). 미해석 제어 바이트 `0x00`(413) `0xFD`(164) `0x08`(67)
`0x0F`(19) 는 아직 규명되지 않았다.

## 한글 출력 성공 (실측)

`tools/patch_hangul.py` → `work/korom_prologue.md`. 화면 확인 완료.
프롤로그 5줄이 한글로 출력되고 나머지 UI(승리/패배 조건문, PLAYER/ENEMY,
숫자, 勝利/敗北 한자 그래픽)는 전부 원본 그대로다.

**새 68000 코드를 한 줄도 쓰지 않았다.** 8x8 한글 폰트(Galmuri7)를 쓴 덕에
음절당 1타일 / 1칸이 되어 업로드 루틴·2바이트 인코딩·렌더러 패치가
전부 불필요해졌다. 고친 것은 셋뿐이다.

```
폰트 타일 37개   안전한 타일 자리에 Galmuri7 8x8 1bpp 글리프 덮어쓰기
$62BC 37엔트리   한글 바이트 코드(0x7F..) -> 타일 번호
대사 79바이트    0x38C42 (원본 자리 186B)
+ 체크섬 우회    0x18E = 0000
```

실기 해상도에서 8x8 한글의 가독성은 확대 미리보기 인상보다 훨씬 낫다.
수직 위치도 줄 안에 자연스럽게 앉는다(렌더러가 가나 하단 타일 행에 찍지만
어색하지 않음).

### 실패에서 배운 것 — 단일 스냅샷으로 타일 사용 여부를 판정하면 안 된다

첫 빌드는 VRAM 스냅샷 한 장에서 "화면에 없는 타일 = 미사용" 으로 판정해
ASCII 타일 36개를 덮어썼다. 그중 타일 17(`1`)이 스테이지 번호에 쓰여
제목이 `고.おうじょう...` 로 깨졌다.

같은 화면이라도 게임은 시점마다 다른 것을 그린다. 스냅샷은 **그 순간** 쓰는
타일만 알려준다. 숫자·알파벳은 UI 전반에 등장하므로 ASCII 영역(0..95)은
통째로 제외하고 가나 영역만 쓴다.

### 테스트 롬의 제약 (최종본에는 해당 없음)

덮어쓸 수 있는 안전 타일이 40개뿐이라 번역문의 **고유 음절을 37자로** 맞췄다.
같은 글자를 여러 번 쓰는 것은 공짜이므로 제약은 글자 수가 아니라 음절 종류 수다.
8x8 은 한 줄 34칸에 34자가 들어가므로 칸은 넉넉하다(최대 21/34 사용).

이 제약은 "기존 폰트 타일을 훔쳐 쓴다" 는 임시 방편에서 나온 것이다.
최종본은 대본이 전부 한글이 되어 가나 타일 전체를 회수할 수 있고,
그때는 메시지별 동적 글리프 업로드로 간다.

## 16x16 시도 — 실패 (기록)

`tools/patch_hangul16.py`. ASM 없이 16x16 을 만들려는 요령이었다.

`0x0D` 은 `Y += 1`, 즉 타일 한 행만 내려간다(`$6604` 의 `lsl.w #$7, d2` = `Y * 0x80`,
행 피치 0x80 = 64엔트리 = 한 타일 행). 그래서 한 줄을 두 번 써서
`[상반부 타일들] 0x0D [하반부 타일들]` 로 깔면 세로로 붙은 16x16 이 될 것으로 봤다.

**결과: 하반부 한 줄만 화면에 나왔다.**

검증한 것 — 모두 정상이었다:
- 메시지 바이트: 상반부 32B + `0x0D` + 하반부 32B 로 정확히 기록됨
- `safe_tiles.json` 에 중복 롬 오프셋 없음 (타일 40개 / 오프셋 40개)
- Galmuri11 글리프는 상·하반부 각각 4~5행씩 잉크가 있음 (상반부가 비어서가 아님)
- `$6604` 주소 계산상 `0x0D` 하나 = 8px 가 맞음

남은 가설은 두 줄이 같은 행에 겹쳐 그려져 나중에 쓴 하반부가 상반부를 덮었다는
것이다. 확정하려면 이 롬으로 VRAM 을 떠서 네임테이블을 봐야 한다.

**더 파지 않기로 했다.** 16x16 을 제대로 하려면 글리프 상하반부를 한 번에 찍는
렌더러 코드를 새로 써야 하고, 이 요령은 그걸 피하려던 우회였다. 동적 글리프
업로드를 만들 때 68000 코드를 쓰게 되므로 렌더러도 그때 같이 손대는 것이 맞다.
지금 원인을 파는 것은 곧 버릴 코드를 디버깅하는 것이다.

### 결론

```
8x8   채택. 5줄 전체 정상, 실기 가독성 충분, ASM 불필요
16x16 보류. 렌더러 신규 작성이 전제 — 동적 업로드 작업 때 재검토
```

## 동적 글리프 업로드 — 3회 실패, 원인 규명

`tools/asm.py`(손 어셈블 68000 + capstone 왕복 검증), `tools/build_dynamic.py`.

### 검증된 성과 (한글 출력과 무관하게 유효)

- 롬 1MB 확장이 부팅에 문제없다
- 대본을 `0x90000` 으로 이설하고 포인터 테이블을 고쳐도 동작한다
- 손으로 어셈블한 68000 코드를 롬에 심어도 부팅이 깨지지 않는다
- 텍스트 코드를 `0x7F..0xA0` / `0xE0..0xFD` 로 제한하면 남은 일본어가 온전히
  보존된다. `$62BC` 를 항등 매핑하면 가나 바이트(0xA1..0xDF)를 덮어써
  제목·승패 조건문이 깨진다(실측 확인).
- 롬에 빈 공간이 0바이트다. 확장 없이는 코드를 넣을 자리가 없다.

### 실패 원인 세 가지 (순서대로 드러남)

1. **`0x1556C` 는 죽은 코드다.**
   ```
   015560  move.w #$2, d0
   015564  cmpi.w #$2, d0
   015568  beq.w  $15650    <- d0 은 항상 2 이므로 항상 분기
   01556C  ...              <- 도달하지 않는다
   ```
2. **`$E818 == $E82C` 로 메시지 시작을 판별할 수 없다.**
   인터프리터가 `0x1536E` 에서 두 값을 같게 만든 뒤 워드를 읽어가며 포인터를
   전진시켜 `$E818` 에 다시 쓴다. 텍스트 렌더 시점엔 이미 다르다.
   → 우리가 심은 마커 바이트(`0xFE`)로 판별하도록 바꿨다.
3. **프롤로그는 `$E818`/`$E82C` 경로를 쓰지 않는다.**
   프롤로그 화면의 CPU RAM 덤프에서 `$E818` `$E82C` `$E81C` `$E81E` `$E820` 이
   **전부 0** 이고, 프롤로그 텍스트 주소(`0x38C42`)가 워크 RAM 어디에도 없다.
   포인터 테이블에서 읽어 레지스터로만 쓰고 버린다는 뜻이다.
   `0x15576` 과 `0x15650` 은 전투 중 대사용 경로다.

### 다음 시도의 방향

메시지 렌더러마다 훅을 거는 방식은 텍스트 경로가 여러 개(프롤로그·전투 대사·
메뉴)라서 경로별로 다 찾아야 한다. 대신 **모든 텍스트 경로가 공유하는
타일 출력 루틴 `$5EFE` 에 훅을 거는 것**이 경로 독립적이다.

`$5EFE` 는 `$62BC` 를 참조해 타일 하나를 찍는 유일한 지점이므로, 여기서
"이 코드가 한글 범위면 글리프를 슬롯에 올리고 그 슬롯 번호로 찍는다" 를
구현하면 어느 경로든 동작한다. 렌더러가 타이프라이터식으로 글자를 하나씩
그리므로 글자당 타일 1개 업로드는 비용도 감당 가능하다.

슬롯 배정 전략이 남은 설계 문제다. 한 화면에 최대 170자가 뜨는데 슬롯은
94개(가나를 전부 회수하면 ~160개)라, 화면 단위 중복 제거나 라운드로빈 중
어느 쪽이 안전한지 따져야 한다.

## 동적 글리프 업로드 성공 (4번째 시도)

프롤로그 5줄이 완전판 56글리프로 출력된다. **음절 37자 제약이 사라졌다.**

### 통한 이유 — 순서를 바꿨다

1~3차는 코드를 읽어 훅 지점을 추론했고 모두 빗나갔다. 4차는 **포인터 테이블
`0x38BF2` 를 누가 읽는지 역추적**해 실제 호출 지점을 찾았다.

```
018CF4  move.w  $AE6C.w, d7        스테이지 번호
018CF8  lsl.w   #$2, d7
018D18  lea     $38BF2.l, a1       프롤로그 테이블
018D1E  movea.l (a1, d7.w), a1     a1 = 문자열 주소  <- 레지스터로 직접
018D2A  jsr     $5F60.l            <- 이 6바이트를 우리 루틴 호출로 교체
```

주소가 RAM 변수가 아니라 `a1` 에 실려 온다. `$E818` 을 볼 필요가 없고
이 자리는 프롤로그 화면마다 정확히 한 번 실행된다.

`tools/asm.py: build_uploader_a1()` — `d1..d5` 는 `$5F60` 의 인자라 `movem` 으로
전부 보존하고 `d0` 만 쓴다(`$5F60` 이 진입 후 스스로 채우는 것을 확인).
`movem` 마스크 규약은 게임 자체 코드(`0x54AC` 의 `48e7fffe`)와 대조해 검증했다.
끝에서 `jmp $5F60` 으로 꼬리호출해 원래 호출을 이어받는다.

배치: 업로더 `0x80000`, 글리프 테이블 `0x81000`, 이설 메시지 `0x90000`.

### 알려진 결함 — 승패 조건문이 깨진다

글리프 슬롯이 타일 128번부터인데, 같은 화면에 남은 **일본어 승패 조건문이 그
가나 타일을 쓴다.** 프롤로그 본문이 먼저 그려져(`0x18D2A`) 타일을 한글로 덮고,
그 다음 조건문이 그려지므로(`0x18D42`) 덮인 타일이 보인다.

최종본에서는 전부 한글이 되어 가나 타일이 놀기 때문에 문제가 되지 않는다.
지금은 한 화면에 두 언어가 섞여 생긴 충돌이다.

**화면 단위로 해결해야 한다.** 네임테이블은 타일 *번호* 만 들고 있으므로,
나중에 그 타일의 픽셀을 바꾸면 먼저 그려진 글자의 모양까지 바뀐다. 즉 한 화면에
동시에 보이는 모든 문자열은 **하나의 일관된 타일 배정을 공유**해야 한다.

다음 단계: 첫 draw(`0x18D12` 스테이지명)에 훅을 걸어 그 화면 세 문자열
(스테이지명·프롤로그·승패조건)의 글리프 합집합을 한 번에 올리고, 각 문자열이
공유 슬롯을 참조하게 한다. 그러면 충돌이 사라지고 화면이 전부 한글이 된다.

## 프롤로그 화면 전체 한글화 완료

`tools/build_screen.py` → `work/korom_screen.md`. 화면 확인 완료.
스테이지명·프롤로그 5줄·승패 조건문이 전부 한글로 정상 출력되고 위치도 맞다.

### 화면 단위 슬롯 공유

네임테이블은 타일 *번호* 만 들고 있다. 나중에 그 타일의 픽셀을 바꾸면 먼저
그려진 글자의 모양까지 바뀐다. 그래서 한 화면에 동시에 보이는 문자열들은
**하나의 일관된 타일 배정을 공유해야** 한다.

프롤로그 화면 렌더러 `0x18CE8` 이 세 문자열을 순서대로 그린다.

| 호출 | 테이블 | 위치 | 처리 |
|---|---|---|---|
| `0x18D12` | `$38A38` 스테이지명 | X=12 Y=3 | **훅** — 합집합 전체 업로드 |
| `0x18D2A` | `$38BF2` 프롤로그 | X=3 Y=5 | 원본 유지 |
| `0x18D42` | `$3962E` 승패조건 | X=9 Y=15 | 원본 유지 |

첫 draw 에만 훅을 걸고 세 문자열 글리프의 합집합(64개)을 한 번에 올린다.
헤더(마커+ID 목록)는 첫 문자열만 갖고 나머지 둘은 본문뿐이다.

글리프 합집합 64개 / 코드 64개 — 여유가 0 이다.

### 이 단계에서 겪은 실수

**줄바꿈을 이중 적용했다.** 게임은 시각적 한 줄에 `0x0D` 두 개가 필요하다.
`encode()` 가 `\n` 하나를 `0x0D` 두 개로 펼치는데 `ko.tsv` 에도 `\n\n` 을 적어
네 개가 되어 32px 내려갔다. → `ko.tsv` 는 시각적 줄 수만 적는다.

**한 번에 세 가지를 동시에 고쳐 원인을 못 갈랐다.** 프롤로그가 사라진 원인은
줄바꿈 하나였는데, 같은 빌드에서 저바이트 코드 제거와 글리프 감축까지 같이
했다. 다음부터 하나씩 바꾼다.

**`0x0E..0x1F` 코드는 아마 멀쩡하다.** 사라진 원인이 줄바꿈으로 확정됐으므로
예방적으로 뺀 저바이트 18개는 쓸 수 있을 가능성이 크다. 지금 코드 여유가 0 이라
나중에 필요해지면 이것부터 검증한다.

### 남은 일본어·영어

**`PLAYER` / `ENEMY` / `FRIENDLY` / `VS` — 번역하지 않는다 (결정됨).**
어려운 단어가 아니고 그대로 읽히므로 손대지 않는다. ASCII 폰트로
`0x386CA` 등에 있고 `jsr $5F7A` 로 그려진다(다른 루틴). 기술적으로는 가능하다 —
8x8 한글은 음절당 1칸이라 `플레이어`(4칸)가 `PLAYER`(6칸)보다 오히려 짧다.
하지만 가치가 낮고 화면 글리프 예산이 이미 64/64 이므로 하지 않는다.

**`勝利` / `敗北` — 교체 예정.**
폰트가 아니라 그래픽이다. VRAM 타일 `522..541` = 4칸 x 5행 = 32x40px 블록에
두 라벨이 세로로 담겨 있다. 색상 구성은 13(배경)/15/14(외곽선).

조사 결과:
- 4bpp 원형은 롬에 없다 → 그대로 저장된 것이 아니다
- **1bpp(잉크=15) 변환형은 롬 `0x060872`~`0x06090A` 에서 8개가 유일하게 특정된다**
  즉 압축 그래픽 코덱을 역설계할 필요가 없다
- 찾힌 8개는 블록의 1행·3행이고 스트라이드가 16이다. 사이에 끼인 8바이트가
  색상 14 플레인일 것으로 봤으나 **틀렸다**(0/8 불일치). 저장 순서나 인터리브
  방식이 다르다.

형식을 추측으로 맞추지 말고 **이 타일을 VRAM 에 올리는 코드를 찾아 읽는다**
(프롤로그에서 통한 역추적). 타일 522 의 VRAM 주소는 `522*32 = 0x4140` 이므로
그 주소를 만드는 코드를 찾는 것이 출발점이다.

교체 계획: Galmuri11 16x16 으로 `승리` 2자 = 32x16px, `패배` 2자 = 32x16px →
합쳐서 32x32px 로 20타일 중 16타일에 들어간다. 원본의 굵고 큰 인상도 유지된다.
한 번 하면 20스테이지 프롤로그 화면 전부에 적용된다.

   PLAYER/ENEMY 영어         하지 않음
